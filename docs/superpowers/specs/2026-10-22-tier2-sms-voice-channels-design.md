# Tier 2 SMS and Voice Channels (Twilio SMS, BulkVS SMS, httpSMS, Twilio voice call) — Design

Source: master plan (`wxnotify-nextgen-plan.html`, FEAT "Notification channels" table: Twilio "Tier 2 BYO key; SMS/voice", BulkVS "US-based SMS/voice alternative to Twilio", httpSMS "uses the subscriber's own Android phone as an SMS gateway"; the tier table: Free = "Email + 1 no-cost push channel", Plus/Pro = "Any Apprise channel, incl. BYO-key paid services (SMS, voice, etc.)"; RISK "BYO-credential security": encrypted at rest, kept out of logs, a revocation path; the compliance item: "SMS/voice consent and opt-out mechanics under TCPA ... needs actual legal review before Phase 2 puts BYO Twilio/voice channels ... into subscribers' hands"). The owner asked to "just start with SMS and voice first" and left the design calls to us: each one is marked **My call** for the owner to check. The plan is intent, the code is truth; where they differ this is said below.

## Goal

A Plus or Pro subscriber can receive alerts as text messages through their own Twilio, BulkVS or httpSMS account, and as a phone call through their own Twilio account, set up with the same guided create → confirmation-code flow as every other channel, where the code goes to their own number and so also proves they own it.

## What the code already says (facts this design rests on)

- `ChannelType` (`app/Support/ChannelTypes/Contracts/ChannelType.php`) builds `apprise_url` and/or an encrypted `config` (`encrypted:array`) through `buildDestination()`; both columns are excluded from the activity log. `ChannelDispatcher` picks a `Transport` from `ChannelTransport`; transports return fixed-string `DeliveryResult` errors (delivery.md). `BeginChannelConnection` is the one create-and-send-code path (actions.md); the wizard is `ConnectChannel`.
- **`min_tier` is stored in `channel_types` but enforced nowhere.** `User::canAddChannel()` only counts Free's no-cost slot and returns `true` for any type with `countsTowardFreeSlot() === false`, so a type marked "plus" with `countsTowardFreeSlot() === false` would be open to Free today. There are no Plus/Pro channel limits (Plus and Pro are unlimited); tier is `tier_override` only, so a "downgrade" is staff clearing it.
- **Unverified channels are delivered to.** `MatchWeatherAlertRules` sends to every channel on the rule; nothing checks `verified_at` (the alert form's helper text says otherwise). Harmless for a chat webhook, not for a phone number nobody confirmed.
- No short-link service exists in the code (no YOURLS / wxn.io); the shortest link the app has is `IngestedProduct::viewUrl()` (`WXNOTIFY_PRODUCT_DOMAIN`). No sanitised-error helper exists either (the "alert coverage diagnostic" has none); every transport writes fixed strings.
- The queue workers run `--tries=1` (`compose.yaml`), so a job never retries; `AppriseApiClient` lets `ConnectionException` surface; jobs write the `DeliveryLog` row after the send.
- Apprise API container is `caronc/apprise:latest`, currently 2.0.0 (checked in the running container). Its `twilio`, `bulkvs` and `httpsms` plugins take digits for the From host (Twilio adds `+` itself), merge the title into the body (`title_maxlen = 0`), default to `retry = 0`, and send an over-long body upstream unsplit. **Apprise 2.0.0's Twilio plugin can also place a call** (`?method=call`, the body is posted as `Twiml`), contrary to the brief's premise; see "Voice" for why we still go direct.
- The mobile app (`wxnotify-mobile`) creates only types whose `appSetupFields()` is non-null, renders text/email/url/secret inputs only, at most 3 fields, no checkbox. It lists every channel generically (`type_label`, `destination`, `destination_label` from `ChannelResource`) and can verify, resend, test, rename and delete any channel through the API.

## Decisions

1. **Four channel types**, slugs `twilio_sms`, `bulkvs_sms`, `httpsms` (Stage 1) and `twilio_voice` (Stage 2). Labels "Twilio SMS", "BulkVS SMS", "httpSMS (your Android phone)", "Twilio voice call".
2. **Phone types store `config`, not `apprise_url` (My call).** `config` = provider credentials + `from` + `to` (both E.164) + consent record. A new `ChannelTransport::Sms` → `SmsTransport` builds the Apprise URL from `config` at send time and posts through the existing `AppriseApiClient` (SMS still goes through Apprise, per delivery.md). Why: the composed URL would hold an auth token that can spend the subscriber's money, and the Edit form's Reveal action shows any `apprise_url`; with `config` nothing reveals it, `displaySummary()` reads the number without parsing a URL, the duplicate check compares plain `to` values, voice reuses the same shape, and the SMS formatting lives in the transport. Rejected: storing `apprise_url` and excluding these types from Reveal (one more special case to remember).
3. **Tier gating (fixing the gap above).** Catalog rows `min_tier = plus`; the types return `countsTowardFreeSlot() === false`. `Tier::meets(Tier $minimum)` (Free < Plus < Pro) and `User::meetsChannelTier(string $slug)` read the catalog row; `canAddChannel()` checks it first, for every type (all shipped types are `free`, so nothing changes for them). The dispatcher checks it again at send time: a channel whose owner is below its type's `min_tier` gets `DeliveryResult::failed('This channel needs the Plus plan or higher.')`, so a downgraded subscriber's SMS/voice channels stop (and show as failures, which the channel-health view picks up) but are kept, and work again on re-upgrade. **My call:** keep-and-refuse, not delete or auto-detach. A missing catalog row counts as `free` (no surprise outage).
4. **Unverified phone channels never get alerts (My call).** The dispatcher refuses any send other than `meta.type === 'confirmation'` to an unverified channel of a `PhoneChannelType` ("This number has not been confirmed yet."). Fixing it for every type is out of scope (it would change Tier 1 behaviour); flagged for the owner.
5. **Numbers: US/Canada (NANP) only in this batch (My call).** `App\Support\PhoneNumber::normalize()` accepts 10 digits, 1 + 10 digits, and `+1…` with any spaces, dots, dashes or parentheses, requires NXX-NXX (area code and exchange start 2–9), and returns `+1NXXNXXXXXX`; anything else (7 digits, other country codes, letters, extensions) is refused with "Enter a US or Canadian number, e.g. (555) 123-4567." No new dependency (libphonenumber would need approval). Apprise gets digits only (`1NXXNXXXXXX`), Twilio's REST API gets E.164.
6. **Destination is the subscriber's own number**, typed in the `to` field, confirmed by the code. One channel per (type, `to`) per subscriber: connecting the same type to the same number again is refused ("You already have a Twilio SMS channel for that number.") instead of refreshing it (**My call**: refreshing would silently unverify a working channel). The same number on two types (Twilio SMS and Twilio voice) is allowed.
7. **Consent at creation.** Each phone type's form ends with a required checkbox (`accepted`) whose text is a versioned constant `App\Support\PhoneConsent::TEXT` / `VERSION` (draft, `2026-10-draft`): the subscriber owns or may use the number; agrees to automated weather-alert texts/calls to it sent through their own provider account; message, data and provider charges may apply and are theirs; they stop them by deleting the channel (and, where the provider supports it, replying STOP). `config` keeps `consent_version` and `consented_at`; an activity-log entry (event `phone_consent`, properties `channel_type` and `version` only, never the number) records it. This is **not** a compliance claim: the master plan's legal review is an open owner item and blocks offering these types to real subscribers (decision 12).
8. **Opt-out is provider-side.** Twilio handles STOP/UNSUBSCRIBE etc. on its numbers itself and then rejects further sends to that recipient (error 21610), which arrives here as an ordinary failure; START re-subscribes. BulkVS's handling is unknown (spike in its task); httpSMS sends from the subscriber's own phone, so there is no platform keyword handling. In WxNotify, deleting the channel (or pausing the alert) is the opt-out, and it works from the dashboard and the app. Only the Twilio confirmation text says "Reply STOP to opt out." (per provider `optOutHint()`); alerts do not repeat it (segment budget). No inbound SMS handling.
9. **Not creatable inline or in the app (My call).** `supportsInlineCreate() === false` (the alert form's inline create bypasses `BeginChannelConnection` and has no consent box) and `appSetupFields() === null` (Twilio needs 4 fields plus a checkbox; the app has 3 and no checkbox). Channels created on the dashboard appear in the app and can be verified, resent, tested, renamed and deleted there. **No mobile app change.**
10. **Credentials are edited by re-creating (My call).** The Edit form keeps only the label for these types (as for every non-webhook type); `config` never enters the Livewire snapshot (the table's allow-list already guarantees it). An "update credentials" action is a later item.
11. **Failure text is fixed per provider, never Apprise output or a provider body.** Apprise reports only delivered / not delivered, so SMS failures are e.g. "Twilio did not accept the text message. Check the Account SID, auth token, From number, and that your number can receive texts." Voice (direct) maps the HTTP status and a short allow-list of Twilio error codes to fixed sentences (decision 14). The wizard's "couldn't send your code" body becomes provider-specific (`PhoneChannelType::codeNotSentHint()`), because "temporarily unavailable" misleads when the credentials are wrong.
12. **Ship dark until the legal review (My call).** The migration inserts the four rows with `enabled = false`; `ChannelTypeSeeder::SHIPPED` matches. The owner flips them on once the review is done (from the admin catalog when it exists; until then a one-line `channel_types` update). Factory reset restores them disabled.

## SMS message format

`App\Support\Delivery\SmsMessage::compose(string $body, ?string $title, array $meta): string`, called only by `SmsTransport`:

- **Alphabet: GSM-7 basic set only (My call).** `Str::ascii()`, then `[`→`(`, `]`→`)`, `{}~^\|` dropped, other non-printables dropped, whitespace collapsed to single spaces (one newline kept between parts). One emoji or curly quote would turn the whole message into UCS-2 (70 chars a segment); ASCII keeps 160/153.
- **Budget: 306 characters, two concatenated segments (My call).** One segment (160) cannot hold a subject, a useful line and a link. Layout `{title}\n{summary}\n{link}`: title (already prefixed by `MessagePrefix`) cut to 100; link = `meta.url` (the View Product page), never cut, dropped only if longer than 120; summary = the body (already the Brief/1500 text from the job), whitespace-collapsed, filling what is left, cut at a word boundary with "...". The long template body is never sent as-is.
- **Confirmation:** `WxNotify code: 123456. Enter it in your dashboard to confirm this number for weather alerts.` plus the provider's opt-out hint. **Test:** `WxNotify test: "{label}" is working.`
- The wxn.io short link does not exist yet; when it does, it replaces `meta.url` here with no format change (owner item: the plan moves link creation to ingestion).

## Voice (Stage 2)

- **Separate type `twilio_voice`, not an "also call" option on Twilio SMS (My call).** A call is a different destination: subscribers want calls only for the worst alerts, so it must be pickable per rule; it is verified separately (a spoken code proves the line takes calls); its deliveries and failures are logged separately. Credentials are typed again (a "copy from my Twilio SMS channel" picker is a later item).
- **Direct transport, not Apprise's `?method=call` (My call, revisit if the owner prefers fewer moving parts).** `TwilioVoiceTransport` posts to the fixed host `https://api.twilio.com/2010-04-01/Accounts/{AccountSid}/Calls.json` (form fields `To`, `From`, `Twiml`; HTTP Basic `sid:token`), so it gets a definitive status and Twilio's error code to map to fixed text, owns its timeouts and its no-retry rule, and does not depend on a plugin feature new in an unpinned `latest` image. The Account SID is validated `^AC[0-9a-f]{32}$` before it goes in the path, so it cannot change the request target; SSRF guarding does not apply (fixed host), redirects are off.
- **Retry rule: one attempt, ever.** Connect timeout 5 s, total 10 s; no transport retry; a `ConnectionException`/timeout is caught and reported as "Twilio did not answer in time; a call may still have been placed." (never re-thrown, so no queue setting can turn it into a second call); 5xx and 429 are failures, not retries. Twilio 201 = "Twilio accepted the call" = success; whether anyone answered needs status callbacks (later item). Never log the response body, the SID, the token or the number; log only the exception class.
- **Script:** `App\Support\Delivery\VoiceScript::compose(string $body, ?string $title, array $meta): string` returns TwiML: `<Response><Say language="en-US">…</Say><Pause length="1"/><Say language="en-US">Again. …</Say></Response>`, text = "WxNotify weather alert. {title}. {first sentence of the summary, max 200 chars}." ASCII-folded, XML-escaped (`htmlspecialchars(…, ENT_XML1 | ENT_QUOTES)`), no link. Confirmation: "Your WxNotify confirmation code is 1. 2. 3. 4. 5. 6." said twice. Under Twilio's 4000-char `Twiml` limit by construction.

## Testing

All with `Http::fake` for the Apprise container (`*/notify/*`) and `api.twilio.com`; never real network (`preventStrayRequests` is on). Per type: field validation (credential regexes, number formats, consent required), URL building incl. percent-encoded credentials, wizard end-to-end through `ConnectChannel` as a Plus user, Free user refused at pick time and at send time, duplicate number refused, `config` absent from the activity log and the table's Livewire snapshot, API refuses to create. Composer unit tests (GSM-7 folding, budget, link never cut, confirmation text). Voice: request shape, success, 4xx code mapping, 429, 5xx, timeout = one attempt and a failure, TwiML escaping. Seeder/migration drift and factory reset. Real sends are manual (owner's own accounts) and listed in the plan.

## Out of scope

WhatsApp, Google Chat, Mattermost, Rocket.Chat, OneSignal, PagerDuty, IFTTT, Matrix, Bluesky (later Tier 2 batches); inbound SMS / replies; per-subscriber billing or message caps; delivery receipts and call status callbacks; Twilio API keys (`SK…`) and Messaging Service SIDs; non-NANP numbers; editing credentials in place; enforcing verification for non-phone types; the admin channel-catalog editor; the wxn.io shortener.

## Open owner items

- Legal review of consent text, opt-out and TCPA exposure (blocking `enabled = true`).
- A2P 10DLC: US carriers block unregistered 10-digit-long-code application traffic; Twilio/BulkVS subscribers will need a registered campaign or a verified toll-free number. The setup help text says so; whether WxNotify documents more is the owner's call.
- Pin the Apprise image (`caronc/apprise:2.0.0` instead of `latest`) so the plugin behaviour verified here does not drift; keep the Apprise API at its default log level in production (its warning lines include the destination number).
