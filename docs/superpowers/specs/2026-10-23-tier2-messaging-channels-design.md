# Tier 2 Messaging Channels (WhatsApp, Google Chat, Mattermost, Rocket.Chat, Matrix) — Design

Source: master plan (`wxnotify-nextgen-plan.html`, "Notification channels" table: WhatsApp "Tier 2, via Twilio's WhatsApp Business API; real reach in Spanish-speaking US communities, incl. hurricane-prone regions", Google Chat "Business/organization segment", Mattermost and Rocket.Chat "Self-hostable team chat, normally internet-facing by design", Matrix "Self-hostable, normally internet-facing by design; privacy-conscious audience"). The owner said "proceed with the Messaging channels" and opted out of design questions, so each call is marked **My call** for the owner to check. Precedent and base: the built SMS batch (`2026-10-22-tier2-sms-voice-channels-design.md`, Stage 1 plus its fix wave). As before, the plan states intent and the code is what is true; where the two differ, this document says so.

## Goal

A Plus or Pro subscriber can get alerts in a Google Chat space, a Mattermost or Rocket.Chat channel, or a Matrix room, all through their own webhook or bot. They can also get alerts as WhatsApp messages on their own number through their own Meta WhatsApp Business account. Setup is the usual create → confirmation-code flow, and the code is posted to the destination itself.

## What the code already says (facts this design rests on)

- **The SMS batch's pieces carry over.** These are `min_tier` enforcement (`User::meetsChannelTier()`, checked at add time, at send time in `ChannelDispatcher::refusal()` and again in `ConnectChannel` step 2), the encrypted `config` with the Apprise URL built at send time (`SmsTransport` with `SmsChannelType::requiredConfigKeys()`/`appriseUrl()`), `BeginChannelConnection`'s Back/Next pending reuse (for any type), the phone-only code throttle in `DispatchChannelConfirmationCode`, and the full-row catalog drift test.
- **`SmsTransport` is SMS-shaped.** It requires an `SmsChannelType` (a `PhoneChannelType`), always composes GSM-7 through `SmsMessage`, and sends `title: null`.
- **The SSRF guard is `WebhookUrlGuard`.** It requires https, refuses userinfo, requires a plain-ASCII host (`PlainAsciiHost`) and port 443 or ≥ 1024. It refuses blocked names (`localhost`, `.local`, `.internal`, metadata) and private, reserved, CGNAT, NAT64, 6to4 and Teredo addresses. Its public `hostRisk(host, resolved)` is already reused by `TraccarUrlGuard`. Private targets are allowed only when `wxnotify.mode = selfhost` and `wxnotify.webhooks.allow_private_networks`. delivery.md requires every subscriber-set URL to be checked at save **and** at send time, sent with its guard's `requestOptions()` pin (`CURLOPT_RESOLVE`), and never to follow redirects.
- **Apprise (not WxNotify) makes the final connection.** It does its own DNS lookup and follows redirects by default (`asset.http_redirects = True`; a `?redirect=no` URL argument turns this off per URL). Its default timeouts are 4 s connect and 4 s read (`?cto=`/`?rto=`). The Apprise API has no private-network deny list for notify targets: `APPRISE_ATTACH_REJECT_URL` covers attachments only. It has `APPRISE_ALLOW_SERVICES`/`APPRISE_DENY_SERVICES` for schemes. The container sits on the `sail` network next to pgsql, redis and the other services (`compose.yaml`), and the image is still `caronc/apprise:latest` (2.0.0).
- **An unguarded subscriber-host path already exists.** A ntfy channel's optional custom "Server" is sent through Apprise with no SSRF check, and http is allowed (`NtfyChannelType::buildAppriseUrl()`). Tier 1 is out of scope here; it is flagged to the owner.
- **Apprise 2.0.0 plugins** (read in the container, parse-only spikes run):
  - `twilio://SID:TOKEN@w%3A1555…/1555…` puts Twilio in WhatsApp mode (`From`/`To` = `whatsapp:+…`), but it sends only a free-form `Body`. It has no Content SID or template support.
  - `whatsapp://{template}:{token}@{phone_number_id}/{to}?lang=xx_XX&:1=body` sends a Meta Cloud API template message, with `{{1}}` filled from the body (body max 1024). With no template, it sends a free-form text.
  - `mmost[s]://{host}[:{port}][/{subpath}]/{token}` posts to `{subpath}/hooks/{token}`.
  - `rocket[s]://{id}%2F{token}@{host}[:{port}]` posts to `/hooks/{id}/{token}`. Webhook mode has no sub-path; the user:password form logs in and out on every send.
  - `matrix[s]://{token}@{host}[:{port}]/{rooms}`: a token with no user is used as the access token, with no login. **The user:password form logs in and, if that fails, registers an account** (`_send_server_notification`: `_login() or _register()`). `discovery` defaults to **on**: it follows the server's `.well-known` to another base URL. `e2ee` defaults to on, and `_room_join()` **creates** a room for an alias that does not exist.
  - `gchat://{space}/{key}/{token}` posts to the fixed host `chat.googleapis.com`.
  - Every plugin answers only delivered or not delivered: the Apprise API returns 200 or 424, and the Meta and Mattermost error codes stay in Apprise's own log.
- The mobile app lists, verifies, resends, tests, renames and deletes any channel generically (`ChannelsScreen`, no per-type code). It can create only types whose `appSetupFields()` is non-null.

## Decisions

1. **Five types**, with slugs `whatsapp`, `google_chat`, `mattermost`, `rocketchat` and `matrix`. Their labels are "WhatsApp", "Google Chat", "Mattermost", "Rocket.Chat" and "Matrix", and their icons are `fab-whatsapp`, `fab-google`, `fab-mattermost`, `fab-rocketchat` and `fab-matrix`. Catalog sort orders are 15–19; 14 stays reserved for `twilio_voice`, which Stage 2 has not built yet. All are `min_tier = plus`, and all return `countsTowardFreeSlot() === false`.
2. **WhatsApp goes through Meta's Cloud API (`whatsapp://`), not Twilio (My call; this contradicts the master plan).** Alerts are always business-initiated, so they arrive outside any 24-hour customer-service window, and outside that window WhatsApp delivers only a pre-approved template. Apprise's Twilio plugin can send only a free-form body, so Twilio would refuse every alert outside a window (Twilio error 63016). The Meta plugin sends a named template with the body as its one parameter. Twilio WhatsApp would need a direct transport with Content SIDs. That, and a provider choice inside one type, are later items.
3. **What a WhatsApp message can be.** The subscriber creates and gets approval for one **Utility** template in WhatsApp Manager, in the language they pick. Its body holds exactly one variable, which cannot be the very first or last text, for example `WxNotify: {{1}} (from your WxNotify account)`. Every alert, code and test is sent as that template, with the whole WxNotify text in `{{1}}`. Meta refuses a parameter that contains a newline, a tab or more than four spaces in a row, so the parameter is one line of at most 900 characters, leaving room in Meta's 1024 limit for the template's own words. The setup help says all of this word for word, including that Meta bills the subscriber's account per template message and that a test number can reach only the recipients registered on it. **Owner item:** Meta may treat a code sent in a Utility template as an Authentication message and refuse or reclassify it.
4. **Credentials and destinations live in encrypted `config`; `apprise_url` is null for all five (My call).** These are bot tokens, access tokens and webhook secrets that can post as the subscriber. Keeping them in `config` means the Reveal action never shows them and the Edit form is label-only, as for SMS. The Apprise URL is built at send time, and every user-supplied component is encoded with `rawurlencode()`: tokens, room IDs and aliases (`!`, `#`, `:`), sub-path segments, and the template name. Rotating credentials means deleting the channel and creating it again.
5. **A new contract and a sibling transport, not a change to `SmsTransport` (My call).** The new `ByoChannelType` contract holds `failureMessage()`, `confirmationHint()` and `codeNotSentHint()`. `PhoneChannelType` now extends it, and its methods do not change. `MessagingChannelType extends ByoChannelType` adds `requiredConfigKeys()`, `appriseUrl(array $config)`, `serverUrl(array $config): ?string` (the subscriber-supplied server, null for a fixed host), `destinationKey(array $config): string` and `compose(...)`. `ChannelTransport::Messaging` maps to `MessagingTransport`, which checks the required keys, re-checks `serverUrl()` through the server guard, composes, posts through `AppriseApiClient` and returns the type's fixed failure text. A `ConnectionException` propagates, as it does from `SmsTransport`. The SMS types, `SmsTransport` and their tests stay untouched. Folding `SmsTransport` into this transport would save about 20 lines but would edit four types that are already built and reviewed.
6. **None of the five gets an alert or test until it is confirmed (My call).** The dispatcher's unverified gate widens from `PhoneChannelType` to `ByoChannelType`, which still exempts only `meta.type = confirmation`. An unconfirmed channel aimed at a subscriber-chosen server should carry nothing but its code. Tier 1 types are unchanged.
7. **The wizard and the table read hints from `ByoChannelType`.** The Confirm step says where the code went: "We just posted a 6-digit code to your Mattermost channel." When a code cannot be sent, the type's fixed `codeNotSentHint()` is shown, for example "We couldn't post to that Mattermost webhook. Check the URL and that the server is reachable from the internet." Resend works the same way. The `instanceof PhoneChannelType` checks in `ConnectChannel` and `NotificationChannelsTable` become `ByoChannelType`.
8. **One channel per type and destination.** For example, connecting the same Matrix room twice is refused ("You already have a Matrix channel for that room."). The check compares `destinationKey()` values in PHP, because `config` is encrypted. The keys are: Google Chat `space`; Mattermost `host:port/path/token`; Rocket.Chat `host:port/webhook_id`; Matrix `host:port/room`; WhatsApp, the E.164 number (through the phone path). The same destination on two different types is allowed.
9. **Code throttle for the chat types too (My call).** Each code send makes WxNotify's Apprise connect to a host the subscriber chose and post a message with WxNotify's name into it. Unlimited, that turns WxNotify into a scanner and a way to spam a room through a leaked webhook. `DispatchChannelConfirmationCode` therefore limits the four chat types to 5 codes an hour per subscriber and destination (key `chat-code-destination:{user}:{sha256(destinationKey)}`) and 10 an hour per subscriber (`chat-code-user:{user}`). These buckets are separate from the phone buckets, whose keys and limits stay the same. Refusals use the same `ChannelCodeThrottled`, and the same check happens before anything is written. WhatsApp is a phone type and uses the phone buckets.
10. **Not creatable inline or in the app (My call).** `supportsInlineCreate() === false`, because inline create bypasses `BeginChannelConnection`, the server check and the throttle. `appSetupFields() === null`, because the server check is a Filament rule object and WhatsApp needs five fields and a checkbox. The API's `POST /channels` therefore refuses all five. **No mobile app change:** channels created on the dashboard appear in the app and can be verified, resent, tested, renamed and deleted there. A one-field Mattermost or Google Chat app setup can come later.
11. **Failure text is fixed per type**, never Apprise output. Examples: "Mattermost did not accept the message. Check the webhook URL and that the channel still exists." and "WhatsApp did not accept the message. Check the access token, phone number ID, that the template name and language match an approved template with one variable, and that your number opted in." Logs carry only the exception class.
12. **Shipping state (My call).** `google_chat`, `mattermost`, `rocketchat` and `matrix` ship **enabled**. Today Plus comes only from staff-set `tier_override`, so few people can reach them, and the server check (decision 13) closes everything except DNS rebinding, which item 2 in Open owner items covers. `whatsapp` ships **disabled** until three owner items are done: Meta business verification, the template wording and its category ruling, and the consent text review. `ChannelTypeSeeder::SHIPPED` matches, and a factory reset restores these states.

## Subscriber-supplied servers (Mattermost, Rocket.Chat, Matrix)

13. **`App\Support\Delivery\ChatServerGuard` (final), built on `WebhookUrlGuard::hostRisk()` and `PlainAsciiHost`**, with fixed messages that never repeat the URL:
    - **Scheme:** https only. http is allowed (with port 80 or ≥ 1024) only when private networks are allowed, which means self-host mode with the flag set, where a LAN chat server over http is normal.
    - **URL shape:** no userinfo (`@` in the authority), no query and no fragment.
    - **Host:** plain ASCII, with at least one dot or an IP literal. Single-label names (`apprise`, `pgsql`, `redis`) are refused before any lookup.
    - **Port:** 443 or 1024–65535.
    - **Address:** a public address according to `hostRisk()`, and the name must resolve.
    - **IPv6 literals** (`[2001:db8::1]`) are judged like any address; Apprise 2.0.0 parses bracketed hosts.

    The guard runs at **save time** (rule `SafeChatServerUrl` on the URL field, and again in `buildDestination()`) and at **send time** (`MessagingTransport`, before any HTTP; a refusal returns the guard's fixed message).
14. **Redirects, discovery and timeouts.** Every guarded type's URL carries `redirect=no`, `cto=5` and `rto=10`. Matrix also carries `discovery=no` (so `.well-known` cannot move it to another host), `mode=off`, `e2ee=no` and `image=no`. Mattermost carries `image=no`.
15. **DNS rebinding: a documented residual, not solved in code (My call).** WxNotify cannot pin the address Apprise connects to. Passing the IP in place of the host would break TLS certificate checks, and certificate checks will not be turned off. Re-resolving right before the send narrows the window but cannot close it, because a hostile DNS server can answer WxNotify with a public address and Apprise a moment later with a private one. This is the one deliberate exception to delivery.md's "send with `requestOptions()`" rule. The design recording it is the rule's exception: it is listed under "Rules to record" and is not quietly ignored. The real fix is at the network level (Open owner items 2).
16. **Matrix specifics (My call).** The access token form only, never user and password: the password form would store an account password and lets Apprise register accounts on someone else's homeserver. The fields are the homeserver client URL (no path), the access token, and one room, either an ID (`!opaque[:server]`) or an alias (`#name:server`, ASCII `[A-Za-z0-9._=-]` per Apprise's regex). There are no DM targets (`@user`). The help text says three things. First, invite the bot to the room and accept for it; an alias that does not exist would make Apprise create a room. Second, for matrix.org, enter `https://matrix-client.matrix.org`, because discovery is off. Third, **use an unencrypted room**: WxNotify sends without end-to-end encryption, and in an encrypted room clients show the message as unencrypted or may hide it.
17. **Mattermost and Rocket.Chat take the incoming webhook URL, pasted whole (My call).**
    - **Mattermost:** `https://host[:port][/sub/path]/hooks/{26 lowercase alphanumerics}`. Sub-path segments must match `[A-Za-z0-9._~-]+`, and a trailing slash is trimmed. The stored values are `server`, `path` and `token`.
    - **Rocket.Chat:** `https://host[:port]/hooks/{id}/{token}`, both alphanumeric. A sub-path is refused ("Rocket.Chat under a sub-path isn't supported yet."), because Apprise's webhook mode has none. The stored values are `server`, `webhook_id` and `webhook_token`.
    - The user:password and bot-token forms are not offered.
18. **Google Chat takes the webhook URL pasted whole.** The host must be exactly `chat.googleapis.com` over https, with path `/v1/spaces/{space}/messages` and the query's `key` and `token` (token percent-decoded). The stored values are `space`, `key` and `token`. A `threadKey` in the URL is ignored. The host is fixed, so there is no server check.

## WhatsApp numbers and consent

19. **International numbers for WhatsApp only (My call).** WhatsApp's US Spanish-speaking audience often keeps a WhatsApp account on a Mexican or Central American number, and there are no carrier A2P rules for it. `PhoneNumber::normalizeInternational()` accepts everything `normalize()` accepts (giving the same result), and also `+` or `00` followed by 8–15 digits where the country code does not start with 0 or 1; `+1` must pass the NANP rules. It returns E.164. There is still no libphonenumber, so the check is about length and shape, not about valid numbering plans. The new rule is `InternationalPhoneNumber`, with the message "Enter your WhatsApp number with its country code, e.g. +52 55 1234 5678 or (555) 234-5678.". The duplicate check, Back/Next reuse and the throttle compare numbers through `normalizeInternational()`. This is a superset of `normalize()`, so SMS behaviour and throttle keys stay the same.
20. **`IsPhoneChannel` grows two hooks; behaviour does not change for SMS.** `usesFromNumber(): bool` defaults to true; WhatsApp has no From number, because the Phone number ID is a credential. `normalizeNumber(string): ?string` defaults to `PhoneNumber::normalize`. WhatsApp's `to` field uses `InternationalPhoneNumber`.
21. **Consent.** `PhoneConsent::whatsappText()` uses the same `VERSION` and draft status as the SMS text. In it, the subscriber says they own or may use the number, have opted in to automated weather-alert messages to it from their own WhatsApp Business account, accept that Meta's per-message charges are theirs, and know they stop the messages by deleting the channel or by blocking the business number in WhatsApp. It is recorded like the SMS consent (`phone_consent` activity entry; type and version only). The code sent to the number proves ownership. WhatsApp has no reply-STOP keyword handling, so `optOutHint()` is null.

## Message format (`App\Support\Delivery\MessagingMessage`)

- **Chat types:** `{title}\n\n{body}\n\n{link}`. The title is already prefixed. The link is `meta.url` and is never cut. The body is cut at a word boundary with `...` so the whole message fits the type's `maxLength()`: Rocket.Chat 1000 (Apprise's limit), and Mattermost, Google Chat and Matrix 4000. It is sent as Apprise's default text format with `title: null`; Mattermost and Rocket.Chat merge the title anyway. Unicode is kept, with no GSM-7 folding. The Task 1 spike records how Apprise renders text into markdown targets. **Confirmation:** the existing `DispatchChannelConfirmationCode` body. **Test:** the existing test body.
- **WhatsApp:** one line, `{title}: {summary} {link}`. Whitespace runs collapse to one space, the line is at most 900 characters, and the link is never cut. Confirmation: `Your WxNotify code is 123456. Enter it in your dashboard to confirm this number for weather alerts.` Test: `WxNotify test: "{label}" is working.` The alert text stays English; translated alert text (master plan es-419) does not exist yet. The subscriber's template language only has to match the approved template.

## Catalog and tiers

- One migration, `2026_10_23_100001_add_messaging_channel_types.php`, inserts `whatsapp` (15, plus, disabled), `google_chat` (16, plus, enabled), `mattermost` (17), `rocketchat` (18) and `matrix` (19), each plus and enabled. It is idempotent like `2026_10_22_100001_add_sms_channel_types.php`, and `down()` deletes the five slugs. `SHIPPED` gets the same rows; `ChannelTypeRegistry::$classes` registers the five classes.
- **Destination summary and caption:**
  - Google Chat: `spaces/••••{last4}`, captioned "Google Chat space".
  - Mattermost and Rocket.Chat: the host (it is not a secret), captioned "Mattermost server" or "Rocket.Chat server".
  - Matrix: the room ID or alias, captioned "Matrix room".
  - WhatsApp: `•••• 5678`, captioned "WhatsApp number".

## Testing

- **Faking:** every Apprise call is faked (`'*/notify/*'`) and DNS goes through the guard's resolver closure; there is no real network. Each type gets:
  - field validation through the fields' own rules;
  - URL building, including a percent-encoding dataset with `/ @ : ? # % space` and a unicode character in every user-supplied part;
  - the wizard end to end as Plus;
  - a Free user refused;
  - a duplicate destination refused;
  - a fixed failure text on 424;
  - a `ConnectionException` that propagates;
  - a secret-exposure check: the raw `config`, the activity log, the failure detail and the edit-modal snapshot never contain the credential;
  - the API refusing to create the type.
- **Guard tests:** private, loopback, link-local, metadata, CGNAT and IPv6 literals; a name that resolves privately; a name that is public at save time and private at send time (the send is refused before any HTTP); single-label hosts; userinfo; query; odd ports; http in cloud and in self-host.
- **Batch-wide:** catalog drift and factory reset. Real messages are a manual check (see the plan).

## Out of scope

OneSignal, PagerDuty, IFTTT, Bluesky; Twilio WhatsApp; inbound messages and replies; delivery receipts; Twilio voice (SMS Stage 2); per-subscriber daily caps; Matrix E2EE and password login; Mattermost and Rocket.Chat bot and user modes; Google Chat threads; editing credentials in place; app and inline creation; translated alert text; fixing ntfy's unguarded custom server (flagged below).

## Open owner items

1. **WhatsApp legal and Meta.** Who reviews the consent text (draft `2026-10-draft`)? It needs to cover opt-in records for Meta's policy and TCPA exposure for messages to US numbers. Meta business verification, and whether the suggested Utility template wording, including the confirmation code, will be approved or reclassified as Authentication. These block `whatsapp.enabled = true`.
2. **Network-level SSRF mitigation for the cloud deployment (recommended before wide Plus availability).** Put the Apprise container on its own Docker network, not `sail`, with egress through an SSRF-filtering proxy such as Stripe's smokescreen, using `HTTPS_PROXY` in the container (Python `requests` honours it). Alternatively, use host firewall rules (`DOCKER-USER`) that drop traffic from Apprise to RFC 1918, loopback, link-local (169.254.0.0/16, including metadata), CGNAT and the Docker subnets. Either one closes DNS rebinding for every Apprise channel, the existing ntfy custom server included.
3. Set `APPRISE_ALLOW_SERVICES` to the schemes WxNotify builds (`tgram, discord, slack, pover, msteams, ntfy, ntfys, twilio, bulkvs, httpsms, whatsapp, gchat, mmost, mmosts, rocket, rockets, matrix, matrixs`, plus any that ops alerts use), so a malformed URL can never reach another plugin.
4. Pin the Apprise image to `caronc/apprise:2.0.0`. The `discovery`, `redirect`, `e2ee`, the Matrix token-without-user and `:1=body` behaviour verified here must not drift. Keep the Apprise API at its default log level: its warnings include hosts, rooms and numbers.
5. **ntfy's custom server is an unguarded subscriber host today** (Tier 1, http allowed). Should a follow-up apply `ChatServerGuard` to it? That would change Tier 1 behaviour for existing self-hosted ntfy users.
6. Should Twilio WhatsApp, which needs a direct Content API transport, be offered later for subscribers who already have Twilio?
