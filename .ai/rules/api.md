# API

## The mobile API is versioned, bearer-only and scoped to the token's user
Routes live under `/api/v1` in `routes/api.php` and return Eloquent API Resources (Laravel's default `data` wrapper). They authenticate with `auth:sanctum` and `config/sanctum.php` has `guard => []`, so a dashboard session cookie never reaches them. App tokens carry only the ability `app` (`ability:app`) and must never be accepted as, or confused with, the Public API's personal keys (a later, Plus/Pro-only feature with its own abilities). Every query is scoped to `$request->user()`; another user's id is a 404. Responses never include `error_detail`, a channel destination or URL, or any token (except the beacon token returned once by `PUT /location-sharing`).

## The sign-in handoff code is single-use and consumed before it is verified
`POST /api/v1/auth/token` pulls the authorization code from the cache first (under a lock), then checks the PKCE verifier, so a wrong verifier still burns the code and a replay always fails. Every failure answers with the same generic `invalid_grant`. The token is named from the device name stored with the code, never from the request. The deep-link callback carries `code` and `state` as URI path segments, because NativePHP route params come only from the path.

## ability:app also admits a token with `*`
Sanctum treats `*` as granting every ability, and `createToken()` defaults to `['*']`, so a default token passes `ability:app`. Always call `createToken()` with explicit abilities (app tokens: `['app']`), never the default. `ability:app` runs before `ExtendAppTokenExpiry` so a refused token is never extended.

## /push-token never returns, logs or audits the FCM token
`PUT /api/v1/push-token` creates or refreshes the calling app token's `mobile_push` channel (one per `personal_access_token_id`, deleted with the token by the database cascade) and answers 204 with no body; `DELETE` removes it. The FCM token is stored only in the encrypted `config`, plus `device_token_hash` (SHA-256) so a token held by another channel (a phone handed to another account, an older sign-in) is found with a query and that channel is deleted. A registration therefore deletes any OTHER channel, of any account, holding the same token hash: this is intended (a phone that changed hands or was reinstalled) and relies on FCM tokens being high-entropy secrets that only the device itself knows. The stale channel's `deleted` activity row is attributed to its own owner, not to the registering user. Every write pins the activity causer with `withCauser`; a subscriber's rename of the channel label survives a token refresh.

`POST /api/v1/push-token/badge/clear` resets the unread push count (the iOS app icon badge) of the calling token's own `mobile_push` channel only. It accepts no id (the channel is found by `personal_access_token_id` = the current token, so it can never touch another phone or user), answers 204 with no body always (also for a phone with no channel and for an Android channel, a no-op), and writes no activity row (`resetUnreadPushCount()` updates through the base query).

## The location beacon token has one ability and one route, and cascades with its app token
`PUT /api/v1/location-sharing` (app token) mints a Sanctum token with exactly the ability `['location']`, `parent_token_id` = the app token, and is the only response that ever carries it (`GET` never does). It can call only `POST /api/v1/location` (`ability:location`, throttle `app-location`); `ability:app` routes refuse it and that route refuses an app token. It exists because the geolocation plugin keeps its bearer token in plain `SharedPreferences`/`UserDefaults`: never hand the plugin the app token. `personal_access_tokens.parent_token_id` cascades, so revoking or signing out the app token deletes the beacon token at the database level; "Signed-in devices" lists only `['app']` tokens so beacon tokens never appear. `ExtendAppTokenExpiry` slides a beacon token's expiry unchanged (it only extends the token it is given). `PUT` replaces any earlier beacon token of the phone inside one transaction, so a refused `PUT` (tier limit) revokes nothing. A new phone Location must fit the SEPARATE phone allowance (`User::canCreatePhoneLocation()`, `free_phone_locations` 1 / `plus_phone_locations` 2 / Pro unlimited), refused with `error: location_limit` (the code the app already handles) and a phone-allowance message that says to delete a phone location no longer used (stopping sharing or signing out only unlinks a phone location, which still counts; only an UNLINKED one can be deleted); saved places and Traccar devices never use a phone slot. Position writes go through `RecordMobilePosition` (ignores a fix older than the stored one, logging off around the save, address lookup queued by `QueueAddressLookup`). `POST /location` rejects the whole batch with 422 if any point is invalid (the plugin sends exactly one point per request), answers 204 even for a stale point because the plugin ignores the body and never retries, and 404 for a phone with no linked Location.

## A query on a token's link column must never pass a possibly-null value
`where('app_token_id', $beacon->parent_token_id)` with a null `parent_token_id` becomes `app_token_id IS NULL` (Laravel turns `where(col, null)` into `IS NULL`) and would match every unlinked Location, so a beacon token with no parent app token would write to someone's unlinked phone. Guard the null first (return the same answer as an unlinked phone) and add `whereNotNull('app_token_id')` to the query, as `RecordBeaconPoints` does.

## Alert rule and location writes share the dashboard's logic and speak the subscriber's units
`POST/PUT /api/v1/alert-rules` persist through `SaveAlertRule` (the same action the dashboard's Create and Edit pages call), so units, SPC & WPC per-product risk levels, clearing of columns another category owns, and the product/location/channel syncs cannot drift between the two front ends; `AlertRuleParityTest` runs the same scenarios through both. The API takes and returns `threshold_value` and `radius` in the subscriber's own unit system (`AlertRuleResource` converts with `AlertRuleFormUnits::toDisplay`, the request converts back through the action). Validation (`SaveAlertRuleRequest`) mirrors the form per category and re-checks every id against the user. SPC & WPC risk levels: a `product_settings` entry may carry its own `risk_levels` (it wins for that product); the flat `risk_levels` still applies to every product without its own, limited to each product's options, so the mobile editor (flat only) keeps working. `AlertRuleResource` returns each SPC & WPC entry's `risk_levels` and the flat `risk_levels` as their union; the flat matching fields ignore risk levels, so different levels never read as `mixed`. A flat-only save (no entry carries `risk_levels`) whose flat list equals, as a set, the union of the stored products' levels keeps each stored product's own levels (only an added product takes the flat list), because the mobile editor echoes the flat list on every save, a rename included; a flat list that differs applies to every product. Each entry's levels are validated against that entry's own product's options (`SaveAlertRuleRequest::offeredByEntryProduct()`). `DELETE /locations/{id}` honours `LocationDeletionGuard` (409 `location_in_use`, with the alert names as plain strings, not the guard's HTML-escaped summary) and never removes a location a phone keeps current (409 `location_is_a_phone`; unlink by stopping sharing). Maintenance mode answers a write with 503 and a plain-text body (`MaintenanceModeException::render`), not JSON.

## Place search never logs or stores what was searched
`GET /places/search` and `/places/reverse` log nothing about the query or coordinates, write no activity row; search caches by a hash of the query, reverse by the rounded coordinates (plaintext in the cache key, never logged or written to the activity log); the geocoder shares one app-wide one-request-per-second budget between forward and reverse lookups (it lives in `App\Actions\Locations\NominatimRequest`; `ReverseGeocodeCoordinates::RATE_LIMIT_KEY` remains as an alias), and the endpoint goes through `HeartbeatUrlGuard` like every other staff-set URL.

## Channel endpoints send real messages, are throttled per user and never return a destination
`POST /api/v1/channels`, `/channels/{id}/resend` and `/channels/{id}/test` each send a real message (a confirmation code or a test) to a destination the subscriber typed, so they share the `app-channel-send` limiter (10 per hour per user). A confirmation code is attempt-limited in `VerifyChannelConfirmationCode`: after 5 wrong tries the stored code is cleared and only a resend produces another (the dashboard's verify entry points get the same protection). Responses never carry `apprise_url`, `config`, a URL, a token or the code; `destination` is the type's `displaySummary()` (masked for secret-bearing types such as Discord, Slack, Telegram bot tokens and Pushover; the full address for Email), never a URL or token. A `mobile_push` channel is listed but every write answers 409 `channel_managed_by_app` (it belongs to the app's own push registration). Only types whose `appSetupFields()` is not null can be created; the API validates from those descriptors and `ChannelApiParityTest` keeps them in step with the Filament forms.

## The map snapshot returns only the caller's own places and public warning data, and takes no coordinates
`GET /api/v1/map` builds its snapshot server-side: the phone is the Location whose `app_token_id` is the calling token's id (another phone of the same user is just a place), the places are the caller's own locations with a position (ordered by label then id, as the Locations list), and the warnings are public active events. It takes no coordinates (nothing about a position is logged or put in a URL), caps the warnings at `wxnotify.map.max_warnings` with geometry simplified at `wxnotify.map.simplify_degrees` and rounded to four decimals, and takes its `layers` (base maps, radar WMS, attribution) from `config('wxnotify.map')` so they can change without an app release. `GetMapWarnings` keeps only its first 50 anchors, so `GetMapSnapshot` passes the phone first.

## The product search returns public product fields only, never the bulletin text, and is not logged
`GET /api/v1/products` searches the archive of ingested products (public data, but behind the app token). When given, the search text must be 2 to 100 characters (filters alone work), a page is capped at 50, and the text matches only a word of the catalog name that starts with it (not a substring: "tor" must not find "Thunderstorm"), the AWIPS ID prefix (typed spaces are ignored for that match: "AFD MOB" finds `afdmob`) and the WMO header prefix (case-insensitively: the pipeline stores `cccc`, `ttaaii` and `awipsid` in lowercase; `%` and `_` are literal). The archive classifies only some products (`product_id` is set for VTEC products, AFD and a few SPC/WPC ids; ~95% of rows have none), so a catalog product whose `code` is a 3-character AWIPS category (`TAF`, `AFM`, `AFD` ...) also matches the unclassified rows (`product_id IS NULL`) whose AWIPS ID starts with it, in both the `type` filter and the name match; VTEC-style codes (`TO.W`) match by `product_id` only. That fallback reads the expression index `ingested_products_unclassified_category_index`, which must stay spelled identically to `SearchProducts::UNCLASSIFIED_CATEGORY`. It never returns `text`, zones, polygons or any column beyond `ProductSearchResultResource`, and nothing logs or stores what was searched. The office filter maps an office code to its issuing centres through `App\Support\IssuingOffice` (K or P prefix, plus `SJU` → `TJSJ` and `PPG` → `NSTU`). Test products are hidden in production only. `GET /api/v1/product-types` lists the catalog products (active and retired, never drafts) grouped by category for the filter, each as `{id, name, code}`.

## GET /active-alerts returns public event data for the caller's own places only
`GET /api/v1/active-alerts` lists the warnings, watches and advisories in effect at the caller's own located places (the phone included): `{id, event, family, places, expires, view_url}` per event plus `meta.has_places` and `meta.generated_at`. It takes no parameters, never returns zone codes, polygons, coordinates or bulletin text, never another user's places, test products or any other family, looks at the first 25 located places and caches 60 seconds per user. Events are read only through `GetActiveAlertsForLocation::activeFor()`.

## The alerts feed is the phone's: push rows only, read state per group, old builds keep `channels`/`has_failure`
`GET /api/v1/alerts` and `GET /alerts/{id}` list only groups (rule + product, or a lone row) with at least one successful `mobile_push` row; email-only or all-failed groups are neither listed nor found (404). Each entry gains `read` (bool, `! AppAlert::isUnread()`) and the collection `meta` gains `unread_count` (`CountUnreadAppAlerts`, unread GROUPS). `channels` and `has_failure` are computed over the group's push rows only: old app builds still read both keys, the new app ignores them, so keep them. `POST /api/v1/alerts/{id}/read` (`api.v1.alerts.read`) and `POST /api/v1/alerts/read-all` (`api.v1.alerts.read-all`, registered before the `{id}` routes) sit in the `ability:app` group (a beacon token gets 403), answer `200 {"data":{"unread_count":N}}`, and are idempotent and user-scoped; `read` stamps `read_at` on every unread successful push row of the group that exists at call time (rows added since the list was fetched included) in one UPDATE (`MarkAppAlertsRead`), and 404s for an unknown, someone else's or non-feed alert. `read_at` is not mass-assignable: set it with a query-builder `update`.
