# Pipeline

## Product replay
A replay copy (IngestedProduct.replay_of_id set) is created by ReplayIngestedProduct through IngestProductText with is_test=true and wmo_header_key=null: intake dedup (IngestOncePerWmoHeader) is the only reader of ingested_products.wmo_header_key and does not exclude test rows, so a copy carrying the key would make it drop a later real product. IngestedProductObserver sends any replay copy straight to MatchWeatherAlertRules and never to SyncActiveWwa, so replays never write active_wwas; routing to test accounts only relies on MatchWeatherAlertRules' is_test -> is_test_account filter, which must not be loosened. Replaying is refused in production inside the action itself, not just hidden in the UI.

## Area Forecast Discussion is an ordinary Weather Alerts product, not its own category
There is no forecast_discussion alert category any more: AFD is a catalog product (family `forecast_discussion`, category Other Forecasts, Outlooks, Discussions, and Reports) that a Weather Alerts rule attaches like any other, and MatchWeatherAlertRules matches it through the same product-attachment path as every other product. A rule attaching only AFD never matches another product from the same office, because the rule's own product list is the filter -- never reintroduce a WFO-only check that skips it. `BuildAlertRuleOptions::WEATHER_FAMILIES` (read by the wizard's product table, the API request validation and the app's options) must keep `forecast_discussion` or AFD silently disappears from the picker.

## Office-wide products match a location by the office that covers it
AFD (and any later product like it) is `has_ugc = false` and `has_polygon = false`: it is issued for a whole NWS office's area, so a location has no zone or polygon to be inside of. In Location mode (and Polygon mode, which already falls back to the Location check for a product with no polygon) `MatchWeatherAlertRules::matchesLocationOffice()` therefore matches such a product when its issuing office (`cccc`) is the office covering the location, read from the location's cached forecast zone (`public_zones.cwa`), else its county (`counties.cwa`). It applies only to a Weather Alerts rule, only when the catalog product has neither UGC codes nor a polygon, and only when this bulletin lists no UGC codes of its own (a bulletin that does is matched by them, never by office); SPC & WPC rules never use it (national centres, no local office), and County/Zone mode stays UGC-only because the rule names explicit codes. It rides on the zone cache `LocationZoneObserver` already clears when a location moves, so no extra invalidation exists. This reverses the earlier rule that only Nationwide and WFO modes could ever fire for AFD (a Location-mode AFD rule silently never delivered). A product only reaches a rule once `ExtractProductMetadata` can identify it: today its non-VTEC crosswalk knows AFD only, so other office products (HWO, PNS, LSR...) need their confirmed AWIPS ids added there before any matching mode can deliver them.

## A wrong AWIPS id in the crosswalk fails silently, so confirm it against real traffic
`ExtractProductMetadata`'s non-VTEC crosswalk keys (`AWIPS_PREFIX_CROSSWALK`, `AWIPS_EXACT_CROSSWALK`) must be the lower-cased PIL exactly as it appears in `ingested_products.awipsid`; a key that does not match resolves no `product_id`, the bulletin is stored with `product_id` null, and no rule ever matches it, with no error anywhere. The SPC fire weather outlooks sat unmatched for weeks under `fwdy1`/`fwdy2` while the real ids are `fwddy1`, `fwddy2` and `fwdd38` (doubled D). Before adding or trusting a key, look at the real rows (`SELECT lower(awipsid), count(*) FROM ingested_products WHERE product_id IS NULL GROUP BY 1 ORDER BY 2 DESC`) and the sample in `database/product_examples/`, and test it by ingesting that sample through `IngestProductText` and asserting the delivery, not by calling the extractor with an id the test made up.

## A bulletin is a list of sections; rules match its segments, never its first zone block or VTEC line
A VTEC text bulletin is several sections separated by `$$`, each with its own zone line, one or more VTEC lines and polygon, but `ingested_products` keeps only the FIRST zone block and FIRST VTEC line, so a bulletin's own `ugc_codes`, `product_id` and `vtec_*` describe its first section only. `BuildBulletinSegments` (the first step of `ProcessIngestedProduct::handle()`, for every bulletin with `vtec_office`, replays included) stores one `ingested_product_segments` row per (section x VTEC line), and `MatchWeatherAlertRules` checks a rule segment by segment through `IngestedProduct::asSegment()`. A rule with any matching segment gets one delivery per channel carrying all its segment ids (`delivery_log_segment` records them; the subject names each event once, joined with " + "). Build the segments in the job, never in `IngestProductText`: the observer queues the job from the model's created event, before the ingest action returns. Never decide whether a rule matches a VTEC bulletin from its own `ugc_codes` or `product_id` when it has segments. The segment-less path (non-VTEC products, factory rows) must keep working, and a text bulletin whose sections cannot be read falls back to one segment copied from its columns. `SyncActiveWwa::syncFromCap()` still skips matching a CAP message that has a paired text bulletin; that is safe only because the text bulletin's segments are complete, so a parser regression that drops sections silently drops alerts. `ParseUgcLine` must accept a range on a full code (`CAZ110>114`), wrapped zone lines and a prefix change inside a line: 8.5% of stored bulletins once yielded no zones at all because it did not.

## An active event is many zones: coverage lives in active_wwa_areas, not on the event row
`active_wwas` is one row per VTEC event, but NWS issues an event as many bulletins (the CAP feed sends one message per zone group), so the row's own `ugc_codes` and `polygon` only describe the LAST bulletin and used to overwrite each other: 21% of active events had lost zones, which is how a Hurricane Watch in effect at Destin went missing from Active now. Where an event is in effect is `active_wwa_areas` (one row per event and zone, with its own status, end and optional polygon). `ApplySegmentToCoverage`, called by `SyncActiveWwa` for every segment of a bulletin, is the only writer: NEW/CON/EXT/EXA/EXB/COR/ROU set the segment's zones Active, CAN and UPG set them Cancelled, EXP sets them Expired, each only for the segment's OWN zones, and the event row's status, start and end are derived from its zones, never set from the last bulletin's action. A zone row written by a newer bulletin (`applied_at`) is not overwritten by a late older one, a CAP polygon only fills a zone that has none, and a text segment without a polygon never clears one. Readers (`GetActiveAlertsForLocation`, the polygon lookup for a follow-up statement) read the rows, the polygon authoritative per row; the event's own `ugc_codes`/`polygon` are a fallback for an event with no rows only. `active-wwas:rebuild` repairs events from their stored segments (run `bulletins:parse-segments` first) and, like `ApplySegmentToCoverage`, sends nothing. An upgrade (UPG) now ends its zones; it used to leave the old event Active until it expired.

## A product-based rule is matched product by product, by that product's own settings
For Weather Alerts and SPC & WPC rules, `MatchWeatherAlertRules` decides each product's match from `AlertRule::settingsFor($productId)`: that product's matching mode, WFO, county/zone codes and locations, read from the `alert_rule_product` pivot row and `alert_rule_product_location`. One rule can therefore watch a polygon product, a location product and a WFO product at once, and a product outside its own locations never fires while a sibling does. Never read the rule's own `matching_mode`, `wfo`, `county_zone_codes` or `alert_rule_location` to match a product-based rule. The one exception is built into `settingsFor()`: a pivot row with no `matching_mode` inherits the rule's own mode, WFO, zones and locations, which is how rules, tests and factories that attach products the old way (`$rule->products()->attach(...)`) keep working, and part of the rollback net for the release that introduced per-product settings. Risk levels are per product too: `matchesRiskLevel()` and `matchesRiskArea()` read `AlertRule::riskLevelsFor($productId)`, never the rule's own `risk_levels` (`.ai/rules/models.md`). The matcher eager-loads `products`, `locations` and `productLocations` once per run; a new reader of a rule's settings goes through `settingsFor()` so it does not add a query per product.

## Never dispatch a unique job inside a DB transaction with the database cache store
With `CACHE_STORE=database` on Postgres and `DB_CACHE_LOCK_CONNECTION` unset, a `ShouldBeUnique` dispatch inside `DB::transaction()` that hits a held lock aborts the transaction (the lock INSERT shares the app connection and the fallback UPDATE then throws), poisoning every following query. Today `dispatchOrSuppress()` runs AFTER the per-rule `DB::transaction()` in `matchesGeographySafely()`, never inside it: keep it that way, or set `DB_CACHE_LOCK_CONNECTION` to a second pgsql connection entry. The test suite uses the array cache and cannot show this.

## SPC outlook pairing: WMO header time, shared filter, wait, reverse merge
SPC publishes the Day 1 Convective Outlook as `swody1` (text) and `ptsdy1` (areal outline with risk areas) within about a second, in either order. `BackfillOutlookRiskAreas` pairs them on the WMO HEADER's DDHHMM (third token of `wmo_header_key`, six digits; NEVER the `wmo_ddhhmm` column: NWWS stores the XMPP issue time 1-3 minutes earlier than the header while EMWIN stores the header time, so a mixed-source pair would never pair); a null/malformed key means no pairing and never throws. One shared candidate filter on the immediate path, the delayed check (`PairOutlookAreasAfterDelay`, unique per outline, default 60 s, `WXNOTIFY_OUTLOOK_PAIRING_DELAY_SECONDS`, 0 and the `sync` queue mean no delay and no reverse merge) and the reverse merge (`mergeWaitingOutline()`, called from `ProcessIngestedProduct` just before the single match): same `product_id`, `awipsid = 'swody1'`, `is_test = false`, `replay_of_id IS NULL`, no risk areas yet, same header DDHHMM, bounded time windows. When a `ptsdy1` arrives first it is not matched alone: the delayed check merges into the swody1 if it arrived, else falls back to the standalone match (never lose the alert); the swody1 that arrives meanwhile picks up the waiting outline's areas before its first match through a guarded `whereNull('risk_level_polygons')` update (merge once, strict window so an outline that already fell back is never merged). Re-matching the swody1 stays safe because `DeliverWeatherAlert` is unique per rule+channel+product. `ProcessIngestedProduct` and `PairOutlookAreasAfterDelay` belong to this rule.

## SPC pairing no longer assumes one FIFO queue
With the `deliveries` priority queue, swody1's first delivery can run before ptsdy1's ProcessIngestedProduct; the backfill re-match then finds the DeliveryLog row (dispatchOrSuppress guard) instead of the unique lock. Both orders deliver once (OutlookPairingDelayTest). Delivery content never reads risk areas, so sending earlier changes nothing.
