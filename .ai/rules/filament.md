# Filament

## Filament Wizard dynamically-built steps: avoid non-native Select and goToNextWizardStep() in tests
A Wizard step built via `Step::schema(fn (Get $get) => ...)` (fields that only exist once an earlier field's value is known, e.g. a category picker) breaks two things:

1. Any non-native Select in that dynamic step — `->searchable()`, `->multiple()`, or `->relationship()` — throws a browser console error "Livewire Entangle Error: ... cannot be found on component" and silently desyncs its displayed value from the submitted state (looks selected, validates as empty). Fix: use a native `<select>` Select (drop searchable/multiple/relationship; add an explicit `->exists()` rule if you were relying on relationship() for scoping) or `CheckboxList` instead — both use plain `wire:model`, not `$wire.$entangle()`.
2. `Wizard::getCurrentStepIndex()` is a runtime-only PHP property, not part of Livewire's persisted state — it resets to the start step on every hydrate cycle. `goToNextWizardStep()` trusts that (reset) value, so chaining it more than once in a Pest/Livewire test silently re-validates the wrong step. For a `HasWizard` Create/Edit page, skip step navigation in tests entirely: `livewire(CreatePage::class)->fillForm([...all fields across all steps...])->call('create')` works in one shot regardless of step boundaries. If you must drive a hand-built Wizard page (not HasWizard) through real step transitions in a test, call `Wizard::nextStep()` directly with an explicit index instead of trusting `goToNextWizardStep()`'s auto-detection.

Found while building Notification Channels (ConnectChannel.php) and My Alerts (AlertRuleForm.php).

## A Select action's createOptionForm() can't conditionally require its own fields
Inside a single Select::createOptionForm() modal, a field whose ->required() (or presence) is gated on another field in that SAME schema (e.g. a type picker with `->required(fn (Get $get) => $get('type') === 'x')`) does not validate reliably — Filament rejects the correct, present value as missing, confirmed via a failing test where $get() showed the right values but validation still failed. This is a variant of the dynamically-built-Wizard-step bug already recorded above, but happening inside an Action's modal schema instead of a Wizard step.

Workaround: don't put a type-picker + type-specific fields in one createOptionForm(). Instead give the Select one ->suffixActions() entry per type (via Filament\Actions\Action, each with its own fixed, unconditional ->schema() and ->action() that does the create and appends the new id into the Select's state with Set $set / Get $get). See AlertRuleForm::channelsSelect()/connectChannelAction() for the working pattern.

## EditRecord's default save bypasses non-Fillable fields — override handleRecordUpdate() for legitimate admin writes
A model attribute deliberately excluded from `#[Fillable(...)]` (e.g. `User::tier_override` — kept out so a subscriber can't self-grant a tier) also gets silently dropped by an ADMIN's own legitimate edit form, because `EditRecord`'s default `handleRecordUpdate()` calls `$record->update($data)` — plain mass assignment, same guard either way. No error; the field just doesn't save. Caught by a browser test (saved a value, reloaded, field was still null), not by anything sooner.

Fix: override `handleRecordUpdate(Model $record, array $data): Model` on that specific Edit page to `$record->forceFill($data)->save(); return $record;` — bypasses the guard only on that one intentional, staff-only path. Every other write path to the field stays blocked.

Also: testing a resource that lives on a non-default panel (this app's default is `dashboard`; `admin` is not) needs `Filament::setCurrentPanel('admin')` in the test's `beforeEach()` — without it, `livewire()` throws `RouteNotFoundException` for `filament.dashboard.resources.*` since Filament resolves nav/breadcrumb URLs against the default panel unless told otherwise.

Found while building the Admin Tools UserResource (Support/impersonation).

## A TextColumn deriving a label from a nullable dot-relation attribute needs ->state(), not ->formatStateUsing() alone
`TextColumn::make('someRelation.attribute')->formatStateUsing(fn (?string $state) => $state !== null ? 'A' : 'B')`, intended to render one of two labels depending on whether a related row exists, silently never shows the "null" branch's label. Root cause, confirmed by reading `vendor/filament/support/src/Concerns/HasCellState.php`'s `getState()`: when the raw state resolved from the record (here, a `null` because the relation doesn't exist) is `blank()`, Filament substitutes `getDefaultState()` (the `->default()` value, or `null` if none was set) *before* `formatStateUsing()` ever runs — the formatter closure is never invoked for a blank raw state, only for a non-blank one.

Fix: compute the label from the record instead of a dot-relation path — `TextColumn::make('status')->state(fn (Model $record) => $record->someRelation !== null)->formatStateUsing(fn (bool $state) => $state ? 'A' : 'B')`. `->state()` supplies a state that's never blank in the "false" case (a real boolean), so the formatter always runs.

Found while building the ShapefileLayerResource list page (`Status` column showing "Pending review" vs "Up to date" based on whether a `pendingVersion` relation exists).

## tonegabes/filament-better-options v1.4's Heroicons fallback indicator icon doesn't exist
`RadioCards`/`RadioList`'s default (unconfigured) radio "idle" indicator resolves to `heroicon-o-circle` (`ToneGabes\BetterOptions\Services\IconResolverService::heroiconDefault()`), which isn't a real Heroicons icon — confirmed no outline or solid `circle.svg` ships in the installed `blade-ui-kit`/heroicons set. Every unselected card throws `Svg by name "o-circle" from set "heroicons" not found` the moment the component renders (i.e. immediately, not just on interaction) — only affects the default; the selected-state default (`heroicon-s-check-circle`) is real and unaffected. Only triggers when the optional `tonegabes/filament-phosphor-icons` package (which has its own defaults) isn't installed.

Fix: call `->hiddenIndicator()` on the field, or set explicit `->idleIndicator('heroicon-...')`/`->selectedIndicator(...)` values with icons that actually exist — don't rely on this package's unconfigured default.

Found while swapping `ConnectChannel.php`'s channel-type `ToggleButtons` for `RadioCards` (Better Options plugin).

## A hidden field's Set() clear in afterStateUpdated doesn't survive an EditRecord save
Setting a field to null via `Set $set` inside another field's `->afterStateUpdated()` (e.g. clearing `alert_template_id` when `category` changes away from a value that supports it) only updates in-memory form STATE. If the cleared field's own `->visible()` now evaluates false, Filament's default `isDehydratedWhenHidden(false)` means `dehydrateState()` (`vendor/filament/schemas/src/Components/Concerns/HasState.php`) removes that key from `$data` entirely at save time -- it does not dehydrate the already-cleared value. `EditRecord`'s default `handleRecordUpdate()` does `$record->update($data)` (mass assignment), so a key that's simply absent leaves that DB column untouched -- a record that already had a real value before the field was hidden keeps that stale value forever, even though the live UI and a fresh Create both show it cleared.

Fix: don't rely on the `Set`-in-`afterStateUpdated` clear alone for an Edit page. Also override `mutateFormDataBeforeSave(array $data): array` on that Edit page to force the field to its cleared value there, independent of dehydration. Verify with a real `livewire(EditPage::class, ['record' => ...])->set('data.category', ...)->call('save')` test asserting the DB value, not just `assertFormSet()` -- the in-memory state can look correct while the persisted value is stale.

See `AlertRuleForm::clearAlertTemplateIfCategoryUnsupported()` + `EditAlertRule::mutateFormDataBeforeSave()` for the working pattern.

## A nested dehydrated(false) field (e.g. config.secret) leaves an empty parent array that wipes the column on save
A read-only display field with a dotted state path (e.g. TextInput::make('config.secret')->dehydrated(false)) on a form for a model attribute cast to array/encrypted:array still yields `config => []` in the dehydrated data. EditAction / EditRecord then mass-assigns that empty array over the real (encrypted) value, silently destroying it (found via NotificationChannels: editing a webhook channel's label wiped its url and secret). Fix at the save site, e.g. EditAction::mutateDataUsing(fn ($data) => Arr::except($data, ['config'])), or use a flat non-model-path field (formatStateUsing from the record + dehydrated(false)) so no parent key is ever produced. Sibling of the alert_template_id hidden-field trap above.

## Array-attribute forms: use flat fields converted by the domain class; dynamic Wizard steps get no defaults; keyed groups rename children
(1) The nested `config.*` dehydrated(false) trap: for the webhook channel the fix is NOT Arr::except on save but flat, non-model-path fields converted to/from the array attribute by the domain class (WebhookChannelType::formFromConfig()/configFromForm(), wired through mutateRecordDataUsing() + using()). The merge must be key-by-key over the existing value, because a hidden field is simply absent from $data and must not blank what is stored. Arr::except(['config']) stays the cheap option for channel types whose form never writes the column. (2) A dynamically-built Wizard step (Step::schema(fn (Get $get) => ...)) never gets its field ->default()s: Schema::fill() runs at mount() when the step is still empty and Wizard::nextStep() fills NULLS on the arriving step. Seed defaults from the controlling field's afterStateUpdated (see ConnectChannel::resetSetupStep()) and clear the other branches' field names in the same pass. (3) Group::make(...)->key('x') renames every descendant's key to x.field, silently breaking assertFormFieldHidden('field') / assertSchemaStateSet(['field' => ...]); leave a purely visual wrapper unkeyed. (4) Filament's KeyValue uses $wire.$entangle() + wire:ignore inside such a step: it works only because resetSetupStep() seeds data.headers = [] before render; this is proven only by Livewire tests, not in a browser — verify manually after touching that step.

## Dynamic Wizard-step entangle bug is about ->relationship()/AJAX, not ->multiple() itself
The documented Filament dynamic-Wizard-step entangle bug (Select inside a `Step::schema(fn (Get $get) => ...)` closure) is triggered by `->relationship()` or other AJAX-entangled state -- NOT by `->multiple()`/`->searchable()` on their own. A plain `Select::make(...)->multiple()->options(fn () => [...])` (options resolved server-side, no relationship()) is safe in this exact context, proven by `AlertRuleForm::countyZoneField()` (browser-verified; it now lives in the county/zone modal of `ProductMatchingTable`) and by the former Locations multi-select (browser- and Livewire-state-verified, no desync; that field was replaced by native checkboxes in the per-product table). Don't avoid `->multiple()` in a dynamic Wizard step on this basis alone -- only avoid `->relationship()`/live AJAX-backed options there.

## Resource widgets & Leaflet maps
**Resource widgets & Leaflet maps.** A widget shown via a Resource page's `getHeaderWidgets()` must also be returned from `Resource::getWidgets()` (that is what registers its Livewire component). Load Leaflet only through `filament.partials.leaflet-loader` (`window.whenLeafletReady`); it shares Pinpoint's `pinpoint:leaflet:loaded` / `window.leafletLoading` / `#leaflet-css` protocol, so keep that interop. Put map logic in a global `window.*` init function called from `x-init` (an x-init expression does not reliably resolve `L`), put `wire:ignore` on the Alpine root, and tear down (clear timers, `map.remove()`) in Alpine `destroy()`. Fetch data with a `#[Renderless]` public method called via `await $wire.method()`, never during render. Render external strings only with DOM nodes / `textContent` (never `innerHTML` or bound popup HTML). A data method on a tier-gated resource's widget needs a matching `canView()` (enforced on every hydrate).

## Tapp TimezoneSelect::getTimezoneFromBrowser() can pre-fill a value the Select then rejects
`getTimezoneFromBrowser()` writes `Intl.DateTimeFormat().resolvedOptions().timeZone` into an empty field client-side. Some browsers (Chromium/ICU) return identifiers outside `DateTimeZone::listIdentifiers()` (`America/Indianapolis`, `America/Louisville`, `Asia/Calcutta`, `Etc/UTC`), and the Select validates against its options, so saving fails with "The selected timezone is invalid" even though the user never touched the field -- on an optional field this breaks an unrelated save such as a password change. The JS-driven set does fire `->afterStateUpdated()` without `->live()`.

Fix: add an `afterStateUpdated` normaliser that runs `Timezones::normalise()` (canonical IANA id via `IntlTimeZone::getIanaID()` where the ICU build has it, else null) when the state is filled but not `Timezones::isValid()`. See `EditProfile` + `EditProfileTimezoneTest`. The Location form's timezone field still has this pre-existing exposure (it is required, so a cleared value would error instead of saving).

## Map widgets share one helper partial and build popups with textContent
The Locations map and the Traccar devices map share `resources/views/filament/partials/map-helpers.blade.php` (`window.wxMapHelpers`: pinIcon, relativeTime, formatTimestamp) next to `leaflet-loader` — a new Leaflet widget must include and use it rather than copy the JS. Popups and captions are built with DOM nodes and `textContent` only (labels, addresses and device names are subscriber/external strings); the only HTML is the pin SVG, whose color comes from constants, and links get their `href` from a server-generated URL. The Locations map reads only the database (GetLocationMap): no Traccar or other external call from that page. Both widgets mirror their resource's gate in `canView()` (so it will start protecting them if a policy is added), but there is no LocationPolicy today, so `LocationResource::canAccess()` returns true for everyone, guests included, and `canView()` is effectively a no-op here. What actually protects the Renderless data endpoint: Filament's Authenticate is registered as Livewire persistent middleware (the update endpoint re-authenticates), the data is scoped to `auth()->user()`, and the component has no public state to tamper with. Data methods on these widgets must ALWAYS scope to `auth()->user()` themselves, because the Locations/Traccar gates may allow everyone.

## expandableLimitedList() needs listWithLineBreaks() on a badge TextColumn
TextColumn::limitList()->expandableLimitedList() only expands when each item is on its own line (listWithLineBreaks() or bulleted()); on a plain badge list Filament array_slice()s the items and shows a non-clickable "+N more" with the rest never rendered (vendor/filament/tables/src/Columns/TextColumn.php, the `! $isListWithLineBreaks || ! $isLimitedListExpandable` branch). Add ->listWithLineBreaks() (badges then stack vertically). Seen in AlertRulesTable's Locations/Channels columns.

## My Alerts widgets read only the database, scope to the user, and derive coverage from delivery logs
The My Alerts header widgets (AlertStatsWidget, NeedsAttentionWidget, ActiveNowWidget) are thin Filament classes over Filament-free actions in `app/Actions/Alerts` that take the `User`; the resource's `canView()` allows everyone, so scoping every query to that user is the protection. They make no external calls. "Covered by your alerts" in ActiveNowWidget is evidence from `delivery_logs` joined to the active warning through the shared VTEC event key (`ActiveWwa::vtecKeyFor()` / the `vtec_*` columns on `IngestedProduct`) — never a re-implementation of `MatchWeatherAlertRules`; a warning issued before an alert existed correctly shows "none". Subscriber-supplied names are rendered with Blade `{{ }}` only, failure rows never expose `error_detail` or a destination, and `GetActiveAlertsForLocation::activeFor()` / `sorted()` are the shared source (and comparator) for active warnings.

The My Alerts page's widgets refresh through one Livewire event, `my-alerts-changed` (`AlertRulesTable::CHANGED_EVENT`), dispatched by the table's Active toggle, row delete and bulk delete; each widget has an `#[On]` no-op listener so it re-renders. A new inline table action that changes alerts must dispatch it too. Widgets sit on read paths, so they must never write through model events that block in maintenance mode or log activity: `ResolveLocationZones` persists its derived zone columns with `saveQuietly()` for exactly this reason (a subscriber viewing the page during maintenance would otherwise get a 503).

## SPC & WPC risk levels are nested per category in the form and stored per product
The SPC & WPC alert form shows a "Risk levels" checklist inside each category section whose products have `risk_level_options` (today Flooding, Fire Weather and Convective Outlooks), named `risk_levels.{category}` like `product_settings.{category}`; options are the selected products' own options and the list is hidden unless such a product is selected. A category's ticks belong to that category's products only: `ProductMatchingTable::toSaveInput()` puts them on each switched-on row of that category (`product_settings[].risk_levels`), `SaveAlertRule` stores each product's share (limited to its own options) on `alert_rule_product.risk_levels`, and `EditAlertRule` fills each checklist with `App\Support\SpcWpcRiskLevels::forForm($rule)` (the levels of the rule's watched products in that category). So "Moderate" under Convective Outlooks never ticks "Moderate" under Flooding (the Excessive Rainfall Outlook). The checklists are seeded to `[]` by `AlertRuleForm::seedProductSettings()` for the same null-checkbox-binding reason as the product lists. Fire risk levels are stored but do not filter yet (no extraction), and the form says so. Filament drops the hidden `risk_levels.{category}` key when no selected product of the category offers risk levels; a row with no ticks then stores `[]` (every level), so no stale level survives. One checklist per category means that levels which differ between two products of the same category (possible only through the API) merge into one list on the next dashboard save.

## The Edit channel form reveals the Apprise URL on demand, never prefilled
`NotificationChannelForm`'s `apprise_url_preview` field (only for a record with an `apprise_url`: Pushover, Discord, Slack, Teams, Telegram, ntfy) starts empty and is filled by its Reveal suffix action through `App\Actions\Channels\RevealChannelUrl`, so the URL is never in the page, the Livewire snapshot or form state until requested; Hide clears it and reopening the modal starts hidden. The field is read-only and `->dehydrated(false)`, deliberately NOT named `apprise_url`, so submitting the form can neither overwrite the real URL nor save a revealed value. `RevealChannelUrl` is owner-only (`user_id === auth()->id()`), refuses while staff impersonate (the Reveal button is disabled too), and writes an activity-log entry (event `revealed`, no properties) on every successful reveal, never the URL. Every Apprise URL is built from the subscriber's own input, so revealing it exposes no platform secret; keep it that way (a channel type that embeds a platform credential in its Apprise URL must not use this field). The table `EditAction`'s modal state is serialized into the Livewire snapshot (`mountedActions[0].data`), so `NotificationChannelsTable` builds it from an allow-list in `mutateRecordDataUsing` (the label plus, for a webhook, the `WebhookChannelType::formFromConfig()` fields), never from the record's attributes: no secret column (`apprise_url`, `confirmation_code`, the decrypted `config`, ids) reaches the snapshot, and a new editable or display field must be added to that allow-list explicitly, or it renders empty (the read-only Channel Type field is one: its value is in the allow-list, and it is `->dehydrated(false)` so `saveChannel()` can never receive it). Its tests assert on the snapshot / `mountedActions` (`json_encode($component->snapshot)`), not only the rendered HTML, because `assertDontSee` cannot see the snapshot.

## The Signed-in devices page scopes to the subscriber in its own query and blocks Revoke while impersonating
`SignedInDevices` lists the signed-in subscriber's tokens whose abilities are exactly `["app"]` (never Public API keys) and re-checks ownership inside the Revoke action; the panel gate allows everyone, so that scoping is the protection. Revoke is disabled while staff impersonate (a disabled Filament action is refused server-side) and logs `revoked` with the device name, never the token.

## A product-per-row table in a dynamic Wizard step: a custom Field of native inputs, not Selects or a Repeater
Built as `ProductMatchingTable` (a custom `Field`, one per product category, with the Blade view `filament.dashboard.alert-rules.product-matching-table`), after a spike (2026-10-12, Filament v5.7.6, real browser, user with 5 saved locations) showed a table-mode Repeater is far too heavy. The view is native inputs with deferred `wire:model` / `$wire.set(..., false)`: a switch, a mode change or a location tick makes no request. Everything per row that can be is client-side Alpine: showing the chosen mode's inputs, its helper text, the search box and "Enable all / Disable all" (which flips only that category). There is one shared WFO `<datalist>` for all rows (not 125 options per row); the locations dropdown renders its checkboxes only while open. "Choose zones" (the county/zone state and codes picker), "Add a location" and the product example modal are Filament actions registered on the field (`registerActions()`), so they need no extra fields in each row. State is `product_settings.{category}`, seeded for every row by `ProductMatchingTable::formState()` from `AlertRuleForm::seedProductSettings()` when the category is chosen (never by field defaults: the step is built dynamically, and a non-native Select with an absent state key throws one entangle error per row). The save input is built once, in `mutateFormDataBeforeCreate/Save()` through `ProductMatchingTable::toSaveInput()`, from the validated, dehydrated form data and reused in `afterCreate/afterSave()`; never build it from raw `$this->data`, where a tampered request could add a `product_settings` key no table validated and persist foreign data. `CreateAlertRule` and `EditAlertRule` set `$hasDatabaseTransactions = true`, because the rule row and its pivots are written in two hooks and must commit or roll back together. Measured weight of the built form (last measured after the example buttons were added): about 6,500 DOM nodes and about 1.9 MB for a full re-render of the Weather Alerts step (5,519 nodes before the example buttons), against 46,853 nodes and 9.6 MB for the Repeater.

What the spike tried: a `Repeater::make("product_settings.{$category}")->table([...])->addable(false)->deletable(false)->reorderable(false)` inside `Step::schema(fn (Get $get) => ...)`, 143 Weather Alerts rows (uuid keys), each with Toggle, Hidden `product_id`, title and description View, native `matching_mode` Select, `location_ids` multiple Select, `wfo` searchable Select, a live `county_zone_state` Select and a searchable multiple `county_zone_codes` Select. Measured: (1) no "Livewire Entangle Error" once every row's keys (`county_zone_state => null` too) were seeded in the Category field's `afterStateUpdated`; unseeded, one error per row. (2) Chosen values were all in `$this->data` after round trips; multiple-select ids come back as strings (`["1","32"]`), not ints. (3) A native mode change made no request; a live Select or an opening searchable Select is one round trip each. (4) 143 rows: 46,853 DOM nodes (324 per row) against a 15,000 limit, an 11.5 MB DOM, a 9.6 MB (440 KB gzipped) response on every full re-render, 1.3 to 1.5 s from click to rows (32,839 nodes even with a native 125-option WFO Select); one 26-row category alone was 8,810 nodes and 1.7 MB. (5) `product_id` (Hidden) survived all round trips.

Filament v5.7 names from the spike, in case a Repeater is wanted elsewhere: `Filament\Forms\Components\Repeater\TableColumn::make('Label')->width('60px')`; a table Repeater takes ONE top-level component per column (several inputs in one cell go in an unkeyed `Group::make([...])`); a title-and-description cell is `Filament\Schemas\Components\View::make('view.name')->viewData(fn (Get $get): array => [...])`; per-row client-side visibility is `->visibleJs("[...].includes(\$get('matching_mode'))")` (the field stays in the DOM, so the node count does not shrink).

## The owner setup checklist is a plugin flow shipped by migration
The flow `owner-setup` (Admin panel, visibility `is_owner`) and its steps are created by `database/migrations/2026_10_18_300001_create_owner_setup_journey.php` with `firstOrCreate` only (flow by `key`, steps by `flow_id` + `key`), so owner edits in the panel are never overwritten (a deleted step would come back only if that migration ran again); change shipped wording with a new migration. Steps tick through the classes in `app/Onboarding/Conditions`. Everything is owner-only: the plugin's `skipWhen` hides the launcher, `App\Filament\Admin\Pages\SetupChecklist` replaces the plugin's ungated progress page (do not call `->progressPage()`), and `OwnerOnlyOnboardingPolicy` (config `filament-onboarding.policies`) closes the flow and condition resources.
