# Support

## Boot-time config mutators must skip config:cache and optimize
Anything that overrides config() from AppServiceProvider::boot() (see ApplyEmailSettings) is captured by `php artisan config:cache`, which boots a full app and dumps config()->all() into bootstrap/cache/config.php. A settings-derived value is then baked in and a later null/"keep .env" override can no longer reveal the .env value. Guard the top of such an action with `app()->runningConsoleCommand('config:cache', 'optimize')` and return. The read itself must also be fail-safe (catch Throwable around the settings read only) so migrate/fresh installs never break.

## Integration endpoints are staff-controlled: SSRF guard belongs in the consuming backend
IntegrationSettings endpoints (translation, short URLs, heartbeat, archival, status page) accept any http/https URL including localhost, private IPs and credentials-in-URL, because internal Docker hosts are legitimate and only staff can edit them. Heartbeat is the first consumer and is covered by HeartbeatUrlGuard (see the Heartbeat pings section). The other endpoints (translation, short URLs, archival, status page) still have no consumer: the first backend that calls Integrations::endpoint() for one of them must apply its own outbound-request safety rather than assume the value is safe. WebhookUrlGuard (app/Support/Delivery) is the pattern for subscriber-facing https targets; HeartbeatUrlGuard is the pattern for a staff-set internal target.

## Heartbeat pings
Healthchecks ping URLs (IntegrationSettings heartbeat_*_url) are staff-set and requested from SendHeartbeatPing once per accepted delivery of that feed (including duplicates). The job re-reads the URL at run time, refuses redirects, checks HeartbeatUrlGuard (http/https, no credentials, no link-local/cloud-metadata; private hosts are allowed on purpose), and must never log the URL — it contains the check's UUID. Failures log only the feed key, throttled to one per feed per five minutes. Dispatch is best-effort (DispatchHeartbeatPing never throws) so a ping can never fail an ingest request.

## Units: imperial is stored, Metric is converted at the edges through App\Support\Units
Every stored and computed measurement is imperial (alert_rules.threshold_value in degF/mph/%, radius_miles in miles; NWS metric data is converted to imperial on ingest). A subscriber's `users.unit_system` only changes how a value is displayed and how form input is converted back, so switching units never changes what an existing alert means. All factors and labels live in `App\Support\Units` (and `ThresholdVariable::{unit,displayValue,canonicalValue,format}` for threshold values) — never add a conversion factor anywhere else (NwsTextUnits' km/h and cm come from Units too), and Imperial output must stay byte-identical. NWS prose (detailedForecast, hourly wind text) goes through `NwsTextUnits::toMetric()` for Metric only, sentence by sentence, reverting a sentence it cannot fully convert. The alert form converts on the Create/Edit PAGES (`AlertRuleFormUnits::toDisplay/toStorage`), not in field hooks, because the value fields sit in a dynamically-built Wizard step; Metric wind thresholds are whole km/h (`ThresholdVariable::displayDecimals`; 0.1 mph storage is coarser than 0.1 km/h), temperatures one decimal. `toStorage` has a no-drift guard (an untouched converted value is never rewritten) — keep it when touching those fields. Stored text (delivery-log subjects, sent notifications) is not rewritten when units change. Raw NWS product text inside alerts stays as issued.

## Timezones: a Location's own timezone wins; the profile timezone is only a fallback
`users.timezone` is optional and never backfilled. `App\Support\Timezones` is the one place that decides what a stored timezone means: `forUser` (validated against `DateTimeZone::listIdentifiers()`, so legacy aliases and garbage count as unset), `forLocation` (Location tz, else the owner's), `forRule` (Location tz, else owner's, else `config('app.timezone')`) — never write `$location->timezone ?? config('app.timezone')` inline again. Unset must keep yesterday's behavior: scheduled alerts fall back to app timezone, quiet hours are NOT suppressed without a resolved timezone (and rules matching no specific Location always deliver), the Location form falls back to browser detection, and the dashboard charts use the newest Location that has a timezone, then UTC. A profile timezone on the Location form counts as a non-blank default, so the coordinate-derived fallback (`seedTimezoneFallback`) does not overwrite it, exactly as it does not overwrite a browser-detected value.

## Traccar URLs must pass TraccarUrlGuard at save and before every request, and never follow redirects
A Traccar server's `base_url` is subscriber-controlled and every Traccar request carries its Bearer token, so `App\Support\TraccarUrlGuard` must pass both when the server is saved (`SafeTraccarUrl` on `TraccarServerForm`) and before each outbound call (`ListTraccarDevices`, `PollTraccarServer`, `GetTraccarDeviceMap`); a refused URL behaves like an unreachable server (null / excluded), logged with a fixed message and the server id only. Every Traccar request must also refuse redirects (`withoutRedirecting()` / `allow_redirects => false`). Cloud is strict (no loopback/private/reserved/metadata, http allowed); only `WXNOTIFY_MODE=selfhost` allows private/LAN hosts, by delegating to HeartbeatUrlGuard (metadata and link-local stay blocked in both modes); an unknown mode is strict. Hosts must be plain ASCII via the shared `App\Support\Delivery\PlainAsciiHost` (no IDN or percent-encoding: curl converts/decodes them, so the guard and the client would look up different names; the webhook and heartbeat guards use the same check) and base URLs carry no query or fragment (the app appends API paths). Guard messages are fixed strings and never echo the URL. A host name is looked up once and the connection is pinned to that vetted answer: every Traccar request must be sent with `->withOptions(TraccarUrlGuard::requestOptions($url))` (null = refused; `[]` = IP-literal host, nothing to pin; a name that does not resolve is refused in BOTH modes, because curl would then do its own unvetted lookup, while save-time `violation()` stays lenient about it in selfhost). The options are `curl => [CURLOPT_RESOLVE => ['host:port:ip,[ipv6]']]`; TLS still validates against the host name, and a trailing-dot host is pinned under both spellings. Pinning does nothing behind an HTTP proxy (the proxy resolves). In `Http::pool` merge each server's options into that request. The webhook, Web Push and heartbeat guards pin the same way (see delivery.md; the shared builder is `App\Support\Delivery\PinnedHost`). Any new Traccar call must go through the guard and use its request options. In tests, `tests/Pest.php` binds a stub-resolver TraccarUrlGuard for every Feature test so fake hosts never hit DNS; override it with `app()->instance(TraccarUrlGuard::class, ...)` to test blocking.

## A failed Traccar poll stores a specific reason, built only from fixed strings
`PollTraccarServer::poll()` returns `['positions' => ?array, 'error' => ?string]` (`__invoke()` still returns just the positions or null), and `traccar:poll-positions` saves `error` to `traccar_servers.last_poll_error`, which the Polling Status column and the create-form probe notification show. The reasons come from `App\Support\TraccarFailure` (`forStatus()`: 401/403 token rejected, 404 check the URL, 429, 5xx, 3xx redirect; `forException()`: from Guzzle's curl errno, 6 host not found, 7 refused, 28 timeout, TLS errors; `MALFORMED`) or the URL guard's own fixed message. They never contain the server URL, exception text, response body or token, because the exception text can carry the URL and Bearer token. New failure kinds must add a fixed string there, not interpolate anything from the request. The device map's "Couldn't reach" list and ListTraccarDevices still report only reachable/unreachable.

## Traccar positions: a well-formed position with no GPS fix is skipped, never written, and never voids the batch
Traccar's /api/positions returns a "last known position" for every device even when it never had a fix; those entries are flagged `valid: false` and/or sit at exactly 0,0. `App\Support\TraccarPosition` is the one definition shared by the poller (`PollTraccarServer`) and the device map (`GetTraccarDeviceMap`): `isCoordinate()` (numeric, finite, within ±90/±180 — a violation still voids the whole response as malformed) and `hasFix()` (false when `valid` is exactly `false` or latitude AND longitude are both 0; a single zero coordinate is a real position). A well-formed no-fix position is simply left out for that device, so the poller keeps the location's last good pin (and does not stamp `mobile_position_updated_at`) and the map counts the device as unplaced. Any new consumer of Traccar positions must use these helpers instead of its own checks.

## Deleting a location or Traccar server must go through LocationDeletionGuard
Deleting a location silently detaches it from every alert's locations list (pivot cascade) and nulls `alert_rules.location_id` (nullOnDelete), so Daily Summary / Threshold / Lightning alerts keep existing but never fire again, with no warning; deleting a Traccar server deletes its mobile locations through the database (no model events) with the same effect. In the subscriber panel every delete path therefore uses `LocationsTable::guardedDeleteAction()` / `guardedDeleteBulkAction()` and `TraccarServersTable::guardedDeleteAction()` / `guardedDeleteBulkAction()` (row, Edit-page header and bulk), backed by `App\Support\LocationDeletionGuard::alertsUsing()` / `alertsUsingServer()` / `summary()`: a single delete is cancelled with a persistent notification naming the alerts; a bulk delete removes the unused records and reports each blocked one through Filament's `reportBulkProcessingFailure(key, message)` (escape labels with `e()`; the body is rendered as HTML). The guard is deliberately NOT on the `Location` model, so staff in the admin panel (LocationsRelationManager) and account deletion are unaffected. A new delete path for locations or servers in the subscriber panel must use these helpers. Test note: reading queued Filament notifications (`new Notifications; ->mount()`) consumes them, so read them once and do not combine with `assertNotified()`.

## Deleting a notification channel must go through ChannelDeletionGuard
The alert-to-channel link cascades on delete, so deleting a channel that is an alert's ONLY channel leaves the alert alive but unable to deliver, with no warning (the alert form requires a channel at creation, but nothing used to stop a later delete). In the subscriber panel the Notification Channels table's row and bulk delete use `NotificationChannelsTable::guardedDeleteAction()` / `guardedDeleteBulkAction()`, backed by `App\Support\ChannelDeletionGuard`: `alertsLeftWithoutChannel()` blocks only when an alert would end up with no channel (a channel shared with other channels on every alert it serves is deleted and detached), and `alertsKeepingOtherChannels()` feeds the confirmation text ("removed from N other alerts"). Bulk delete checks records one at a time against the current state, so selecting every channel of an alert deletes all but the last. Staff in the admin panel and the channel-connect flow's cleanup of a half-set-up channel are intentionally unguarded. The "A, B, C (and N more)" alert list comes from `App\Support\AlertNameSummary` (HTML-escaped; shared with LocationDeletionGuard). `App\Actions\Channels\DeleteChannel` (the mobile API) applies the same guard. A new delete path for channels in the subscriber panel must use these helpers.

## Mobile location addresses come from queued reverse geocoding, rate-limited, cached and guarded
`traccar:poll-positions` queues `ReverseGeocodeLocation` (unique per location, off the polling path, never allowed to fail a poll) after storing a position when `Location::needsAddressLookup()`: the location was never resolved, or is at least `Location::ADDRESS_RELOOKUP_METERS` (100 m) from `address_geocoded_lat/lng`, the position its `address` was resolved for. The job re-checks at run time and skips if no longer needed, the integration is off, or the location is stationary or gone. `ReverseGeocodeCoordinates` asks a Nominatim `/reverse` endpoint (Integrations tab: `reverse_geocoding_enabled`, default on, and an optional `reverse_geocoding_endpoint`; blank means `config('filament-pinpoint.leaflet.nominatim_url')`, i.e. `NOMINATIM_URL`, the public OSM instance), at building zoom, with an identifying User-Agent. Public Nominatim's policy shapes it: one request per second app-wide (`RateLimiter` key `reverse-geocode`; a throttled job is released for 2 s), results cached 30 days by coordinates rounded to 4 decimals (about 11 m) and by endpoint, and never any coordinates in logs. The endpoint is staff-set, so it goes through `HeartbeatUrlGuard::requestOptions()` (private hosts allowed for a self-hosted Nominatim; metadata and link-local refused; pinned; no redirects). A definite no-address answer (`error`) clears `address` and still stores the geocoded position so it is not asked again; a timeout, 429/5xx or unreadable body keeps the old address and retries (released for 60 s, up to 30 minutes, and again on a later poll while `address_geocoded_lat` is null). Addresses are cut to the 255-character column. Written with logging disabled, and `address_geocoded_*` are excluded from the activity log and cleared when a location becomes stationary. Public Nominatim is for light use: for many moving vehicles point the endpoint at a self-hosted instance. Spatie caches the whole settings object forever (`SETTINGS_CACHE_ENABLED`), so after deploying a settings migration (such as the one adding these two properties) run `php artisan settings:clear-cache`, or reading the new property throws "must not be accessed before initialization".

## Client IP: `App\Support\ClientIp`, forwarding headers only from a trusted proxy
Activity alerts name the client IP of the request that caused the event (`MatchActivityAlertRules` reads it at dispatch, in the request, and passes it to the queued `SendActivityAlert`; the job tolerates payloads queued before the field existed). Resolution is `ClientIp::for($request)`: `$request->ip()` by default with every forwarding header ignored (any client can send one), and two opt-in env settings in `config/wxnotify.php` `client_ip`: `WXNOTIFY_TRUSTED_PROXIES` (`*` or comma list of IPs/CIDRs; configures Laravel's `TrustProxies` for the WHOLE app via `ClientIp::configureProxies()` in `AppServiceProvider::boot()`, so `request()->ip()` honors `X-Forwarded-For` for rate limiting and logs too) and `WXNOTIFY_CLIENT_IP_HEADER` (e.g. `CF-Connecting-IP`, believed only when `isFromTrustedProxy()`, falling back to `->ip()` when missing or not an IP). `ClientIp::forActivity($subject)` returns null when the request is staff acting on a subscriber or staff impersonating one, so a subscriber's alert never carries staff's address; guest requests (sign-in, sign-out, registration) and the subscriber's own count. Never read `X-Forwarded-For` or `CF-Connecting-IP` directly, and never add a header trust that is not gated on the connection coming from a trusted proxy. The same request also says how the subscriber reached the app: `AccessChannel::forActivity()` (same staff/impersonation rule as the IP) gives `web` for any session request (including the sign-in page the mobile app opens for its browser sign-in) and `mobile app` for a request carrying an `app`-ability token, and nothing for a public API key, a location beacon or a console/queue context; `SendActivityAlert` appends ` via web` / ` via mobile app` after the address, read with `?? null` like `ipAddress` (queued jobs predate the property).

## A channel type the app can create declares appSetupFields() and needs a parity case
`ChannelType::appSetupFields(User)` returns neutral `ChannelSetupField` descriptors (key, label, input kind, required, help, default, validation rules) or null when the mobile app cannot create the type. Shared rule definitions (a URL pattern constant, `TeamsChannelType::workflowUrlRule()`) are referenced by both the Filament field and the descriptor. Adding a creatable type, or changing a field's rules, needs a sample in `ChannelSetupFieldsTest` and `ChannelApiParityTest`.
