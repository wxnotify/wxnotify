# Delivery

## Channel delivery goes through ChannelDispatcher; subscriber-controlled URLs go through WebhookUrlGuard and never follow redirects
Every send to a subscriber NotificationChannel must go through ChannelDispatcher (SendActivityAlert is the one exception: it sends to an admin-set ActivityAlertRule::apprise_target). Any URL a subscriber controls — webhook URLs and Web Push endpoints — must pass WebhookUrlGuard both when saved and again at send time, and the HTTP client used to call it must NOT follow redirects (Guzzle follows up to 5 by default and would let a public https URL 302 the server to a private/metadata address). Webhooks get this via config('webhook-server.webhook_job') = NoRedirectCallWebhookJob; restoring Spatie's CallWebhookJob reopens the hole. Web Push builds its own Guzzle client with allow_redirects=false and treats any non-2xx (including 3xx) as failure. Never put an exception message, response body, endpoint URL or key material in a DeliveryResult error: build it from fixed strings plus the numeric HTTP status. apprise_url and config are encrypted and must not be logged. New channel types need a channel_types migration AND a ChannelTypeSeeder::SHIPPED entry in matching sort order. Hosts must be plain ASCII for every outbound-URL guard (`WebhookUrlGuard::violation()`/`proxyViolation()`, `HeartbeatUrlGuard`, and Traccar), decided by `App\Support\Delivery\PlainAsciiHost` before any DNS lookup and before the self-hosted private-network shortcut: curl converts international names (fullwidth dots like `127。0。0。1` included) and percent-decodes hosts, so a guard judging the host as written would vet a different name than curl connects to (the heartbeat guard used to allow `http://169。254。169。254/`, because it treats an unresolvable name as allowed). International names must be given in their `xn--` form. A new guard or URL rule must use `PlainAsciiHost`, never its own character check. Every outbound call is pinned to the addresses its guard vetted, so a DNS answer that changes between the check and the connection (rebinding) cannot redirect it: each guard looks the host up once and exposes `requestOptions($url): ?array` (null = refused or the name does not resolve; `[]` = IP-literal host; otherwise `curl => [CURLOPT_RESOLVE => ...]`, built by `PinnedHost::options()`). Webhooks get it in `NoRedirectCallWebhookJob::createRequest()` (`WebhookUrlGuard::requestOptions()`; behind a proxy the PROXY host is pinned via `proxyRequestOptions()`, because the proxy resolves the target — a proxy URL without a port is pinned on curl's default 1080 and the scheme's own default), Web Push in `WebPushTransport` (the pin goes into its Guzzle client's config), and the heartbeat ping in `SendHeartbeatPing` (`HeartbeatUrlGuard::requestOptions()`, whose pin shares the 5-minute verdict cache, so a changed address can fail a ping for up to that long; `violation()` stays lenient about an unresolvable name, request time does not). A new outbound call to a subscriber- or staff-set URL must send with its guard's `requestOptions()`, never just `violation()`. Pinning does nothing behind an environment HTTP proxy.

## Webhook proxy/header guards, no Spatie retries with dispatchSync, and a wall-clock budget for synchronous retries
(1) A webhook channel's proxy_url is subscriber-controlled: it must pass WebhookUrlGuard::proxyViolation() at save AND send time. Its rules deliberately differ from the target URL's (http allowed, credentials allowed, ports 80/443 allowed alongside >=1024) — not an oversight. Extra headers must pass WebhookHeaderGuard at both points too (reserved names incl. Host, Content-Length, Content-Type, Transfer-Encoding, Connection, Upgrade, TE, Trailer, Proxy-Authorization, Proxy-Connection and the configured Signature/Timestamp names). Proxy URL and header values are secrets: like the signing secret and endpoint they must never reach a DeliveryResult error, a log or the activity log. The DNS-vs-client TOCTOU also applies to the proxy host. (2) Never hand Spatie maximumTries() > 1 together with dispatchSync(): the job release()s itself after a failed non-final attempt and returns without throwing, so throwExceptionOnFailure() never fires and the caller records a successful delivery that never happened. Retrying belongs in WebhookTransport's own loop, taking waits through App\Support\Delivery\Pauser so tests bind a recording no-op instead of sleeping. (3) A synchronous transport with subscriber-configurable retries/timeouts needs a wall-clock budget (WebhookTransport::DELIVERY_BUDGET_SECONDS = 50), not just per-attempt bounds: stay under min(queue retry_after, worker --timeout) (90 s / 60 s in config/queue.php) because exceeding retry_after causes a DUPLICATE delivery. Project the next attempt's cost before starting it, and keep in-request sends (confirmation codes) to a single attempt.

## Email channels send through Laravel Mail
The Email channel type uses ChannelTransport::Mail: MailTransport sends App\Mail\ChannelMessageMail (a Markdown mailable, body in an escaped <pre>) through the configured default mailer to the encrypted config['to'], never through Apprise. Failure text is fixed (missing address / mail server could not send): an exception message can carry the SMTP host, credentials or the recipient address. The shared mail theme header (resources/views/vendor/mail/html/header.blade.php) renders the logo from APP_URL plus APP_NAME for every Markdown email, including Filament's; keep custom emails on the Markdown layout so they inherit it. The SMTP mailer timeout is 10 s (MAIL_TIMEOUT) so the synchronous send stays well under the queue worker timeout, per the wall-clock-budget rule above. When `$meta['daily_summary']` is present (a Full Daily Summary for a channel type whose `supportsRichContent()` is true), MailTransport sends App\Mail\DailySummaryMail instead, with the same relay/address checks and fixed failure text; it is still the Markdown layout, with the radar image embedded inline as `cid:radar-snapshot`. DailySummaryMail must be sent, never queued: its constructor registers a closure, so only the plain-data report array travels on the queue. Every other channel type stays on Apprise.

## Channel types caption their destination value
Every channel type implements `destinationLabel()`, a short FIXED caption ("Pushover user key", "Email address") shown in gray under `displaySummary()`'s value in the subscriber's Channels table, so a masked fragment is never an unexplained string. The caption is never derived from the record, so it cannot carry a secret, and `displaySummary()` must still never return a value that alone grants delivery access. A new channel type must supply both; the table shows no caption when the value is `—`. Telegram's value is the bare chat ID (the caption says what it is).

## Mobile push goes through FcmClient: fixed strings only, a delayed token-guarded prune
`MobilePushTransport` sends through `App\Support\Delivery\FcmClient` (service-account JWT signed with openssl; token cached ~55 min; fixed hosts `oauth2.googleapis.com` and `fcm.googleapis.com`; redirects off; one attempt). The device's FCM token is a secret: `FcmResult` and `DeliveryResult` errors are fixed strings plus the numeric HTTP status, never a response body, exception message, token or credential (the body is read only to recognise an `UNREGISTERED` / invalid-token reply). When FCM says the token is dead, the transport queues `PruneMobilePushChannel` with a 60 s delay (so `DeliverWeatherAlert` writes its log row first) and a hash of the failed token; the job deletes the channel only if it still holds that token, so a phone that re-registered survives. On the device the app receives `TokenGenerated` only through the mounted screen's `#[On]` handler (trait `HandlesPushToken` on the feed, Account and welcome-flow screens); the plain `RegisterPushToken` listener is only a background fallback. `PushRegistration::register()` must not gate on the OS permission: Android reports `denied` until the dialog answer, which is recorded after the token event. Every message expires after one hour (`android.ttl` 3600s and the `apns-expiration` header), so a phone that was off never receives stale warnings: FCM's default is four weeks. The plugin creates and owns the high-importance Android notification channel `fcm_default_channel`: every message names it (`android.notification.channel_id`), because without it Android shows a background push in the SDK's fallback "Miscellaneous" channel (default importance, no heads-up banner; seen on the emulator). Device channels (`mobile_push`) are created only by the registration API, are verified on creation, do not use Free's no-cost channel slot and are hidden from the picker through `isAvailable() === false`. The iOS app icon badge is the channel's `unread_push_count`: for an iOS phone (`config['platform'] === 'ios'`) `MobilePushTransport` increments it atomically AFTER the blank-token check and BEFORE calling FCM, and sends the new total as `aps.badge` (never a `data` field); Android gets no increment and no badge. A failed push is not rolled back (the increment is not undone), so the count can run ahead of what the phone received. A channel deleted between load and send makes `incrementUnreadPushCount()` return null, and the transport then answers the fixed failure `This device is no longer registered.` without calling FCM. The app clears the badge and resets the count through the reset endpoint (see the tab-screen note below).

## Device channels are deleted outside the dashboard, so they bypass ChannelDeletionGuard
`mobile_push` channels disappear without the dashboard delete path: sign-out, a dashboard revoke, Account "Turn off", an `UNREGISTERED` prune, and a new sign-in claiming the same token all delete the channel, and the cascade removes its `alert_rule_notification_channel` rows. `ChannelDeletionGuard` only covers dashboard deletes, so a rule whose only channel was the phone goes quiet silently. The safety net is the "alert with no channel" (`alert_no_channel`) row in `GetAlertsNeedingAttention` (the My Alerts "Needs attention" widget). Two test traps: the `sync` queue driver (phpunit) ignores `PruneMobilePushChannel`'s 60 s delay, so an end-to-end `DeliverWeatherAlert` test with an `UNREGISTERED` token would prune the channel before the `DeliveryLog` row exists (production uses the database queue); and the prune job's payload hash is a sha1 of the token compared with the channel's CURRENT token, not the SHA-256 `device_token_hash` column.

## A push about a stored bulletin carries an app link, never an https address
`MobilePushTransport` sends the data `url` the nativephp firebase plugin follows on tap. For an alert whose meta `url` is a public View Product page (`https://host/view-product/{slug}`, nothing else: no query, port or credentials) it is `config('wxnotify.app_product_uri')` + `/` + the base64url of that page address (`wxnotify://product/{link}`, matched by the app's `/product/{link}` route and checked again there by `ProductLinkTarget`); every other push (daily summary, threshold, lightning, the test push, a non-https `APP_URL`) sends `/`, which opens the feed. Do not send the https page address as the `url`: on Android the plugin would put it in the intent data and the phone's browser opens instead of the app. The app link's scheme and host must stay equal to the app's registered scheme and route.

## The app clears the icon badge from every tab screen, with a 5-second poll as the return-from-background signal
In the mobile app, every bottom-nav tab screen (Alerts, Map, Products, Settings: `mobile/resources/views/native/partials/tabs.blade.php`) uses the trait `App\Support\Concerns\ClearsPushBadge` and calls `clearPushBadgeOnOpen()` from `mount()` after the sign-in check; pushed screens (Rules, Locations, Channels, Account, details, editors) and sign-in screens do not, and a return to the tab underneath is caught by the gap below. The trait clears with the server reset (`PushBadge::clear()`) on mount. A push received while the app is open must not leave a badge: `MobilePushTransport` puts `event` = `App\Events\ForegroundPushReceived` and `payload` = `{}` (strings) in the FCM `data` of EVERY iOS and Android push (never `content-available`; the payload must be explicit, otherwise the plugin passes `url`/`type` as named constructor arguments of the event). The plugin dispatches the event in an ephemeral PHP runtime, only while the app is in the foreground; the app's plain listener `MarkForegroundPush` sets a cache flag (`PushState::markForegroundPush()`), and the next 5-second tick reads it (`pullForegroundPush()`: read each tick, cleared when set). On iOS a set flag runs the full `PushBadge::clear()`, so a foreground push is counted on the server and then cleared/reset within 0-5 s. On Android the flag is only consumed: a foreground push is left to the OS (its banner and tray entry stay; Android has no badge number and the server never counts Android channels, so there is nothing to reset). The event class name is duplicated in `MobilePushTransport::FOREGROUND_PUSH_EVENT` and the app's `App\Events\ForegroundPushReceived`: change both, a mismatch silently degrades to the old behaviour (the plugin only logs that the class does not exist). A `#[On]` handler on the screen does NOT see this event (it reaches the ephemeral runtime only). The device path is unverified (iOS `didReceiveRemoteNotification` firing for a foreground alert push only; Android `onMessageReceived` dispatching; the flag visible across runtimes); if the event never fires, behaviour is the old one. Tests pass through `emitNative`, which skips the native layer, so they do not prove the device path. Nothing tells PHP that the app came back from the background (no lifecycle event for v4 yet; replace the poll with the app-lifecycle plugin's foreground event once it supports v4), so `#[Poll(5000)] pollPushBadge()` stands in. An ordinary tick never calls the plugin: it only retries a pending failed reset on the server (`PushBadge::retryPendingReset()`, no request when nothing is pending). A tick that finds the foreground-push flag on iOS, or one more than three intervals (15 s) after the previous one (the screen was not ticking, so the app was in the background), runs the full `PushBadge::clear()`. Never call `clearBadge()` on every tick: on Android it is `NotificationManager.cancelAll()`, and the PHP loop can keep ticking for a while after the app goes to the background, so it would cancel a just-arrived push before the subscriber sees it (and wipe an iOS badge a background push just set). Never call the server on every tick either: that would be a request every 5 seconds per open phone. Known, accepted limitations: a push that lands while the app is in the background followed by a return before the loop stopped ticking (no gap) stays on the badge (and the Android tray) until the next tab open or gap; a flag set in the foreground followed within seconds by a background push can cost one extra iOS clear while the loop still ticks. Sign-out clears the badge locally (`SignOut::clearLocal()`, best effort). The framework re-renders the screen after every poll tick (`NativeComponent::runDuePolls()` then the loop re-renders; no way to skip it), so the tab screens now re-render every 5 seconds: keep their render cheap. In tests the suite binds `Tests\Fakes\NullPushBadge` by default (`tests/Pest.php`), so screen tests' request counts ignore the badge; `PushBadgeTest` and `PushBadgeScreensTest` forget that instance to use the real service.

## The mobile welcome flow shows once per install and asks for nothing on Skip
After the first sign-in `AuthCallback` replaces itself with `/welcome` while `Welcome::shouldShow()` (the flag `wxnotify.welcome.seen`, `WelcomeState`) is unset; the flow sets it at mount. The flag lives in its own cache key, which sign-out never touches and uninstalling removes; never put it in secure storage (that survives an uninstall on iOS). An install that was already signed in before the flow existed is marked seen by `AlertsScreen::mount()` (`markLegacyInstallSeen()`, only with a token). The steps are welcome, offer, push, location, done: the push step is left out when push is already on or the OS refused it, the location step when sharing is on or `can_share_phone_location` from `GET /api/v1/alert-rule-options` is false (then the last screen carries a plan-full note). Skip leaves from any step and asks for nothing: no OS dialog, no "declined" mark. Location is deliberately NOT pre-checked against the OS permission (the plugin's check is async); the system dialog comes only from the Share location button. Settings -> Welcome tour replays it at `/welcome/tour` and must open it with `navigate` (never `replace`): it closes with `back()` and never touches the flag.
