# Delivery

## Channel delivery goes through ChannelDispatcher; subscriber-controlled URLs go through WebhookUrlGuard and never follow redirects
Every send to a subscriber NotificationChannel must go through ChannelDispatcher (SendActivityAlert is the one exception: it sends to an admin-set ActivityAlertRule::apprise_target). Any URL a subscriber controls — webhook URLs and Web Push endpoints — must pass WebhookUrlGuard both when saved and again at send time, and the HTTP client used to call it must NOT follow redirects (Guzzle follows up to 5 by default and would let a public https URL 302 the server to a private/metadata address). Webhooks get this via config('webhook-server.webhook_job') = NoRedirectCallWebhookJob; restoring Spatie's CallWebhookJob reopens the hole. Web Push builds its own Guzzle client with allow_redirects=false and treats any non-2xx (including 3xx) as failure. Never put an exception message, response body, endpoint URL or key material in a DeliveryResult error: build it from fixed strings plus the numeric HTTP status. apprise_url and config are encrypted and must not be logged. New channel types need a channel_types migration AND a ChannelTypeSeeder::SHIPPED entry in matching sort order. Hosts must be plain ASCII for every outbound-URL guard (`WebhookUrlGuard::violation()`/`proxyViolation()`, `HeartbeatUrlGuard`, and Traccar), decided by `App\Support\Delivery\PlainAsciiHost` before any DNS lookup and before the self-hosted private-network shortcut: curl converts international names (fullwidth dots like `127。0。0。1` included) and percent-decodes hosts, so a guard judging the host as written would vet a different name than curl connects to (the heartbeat guard used to allow `http://169。254。169。254/`, because it treats an unresolvable name as allowed). International names must be given in their `xn--` form. A new guard or URL rule must use `PlainAsciiHost`, never its own character check. Every outbound call is pinned to the addresses its guard vetted, so a DNS answer that changes between the check and the connection (rebinding) cannot redirect it: each guard looks the host up once and exposes `requestOptions($url): ?array` (null = refused or the name does not resolve; `[]` = IP-literal host; otherwise `curl => [CURLOPT_RESOLVE => ...]`, built by `PinnedHost::options()`). Webhooks get it in `NoRedirectCallWebhookJob::createRequest()` (`WebhookUrlGuard::requestOptions()`; behind a proxy the PROXY host is pinned via `proxyRequestOptions()`, because the proxy resolves the target — a proxy URL without a port is pinned on curl's default 1080 and the scheme's own default), Web Push in `WebPushTransport` (the pin goes into its Guzzle client's config), and the heartbeat ping in `SendHeartbeatPing` (`HeartbeatUrlGuard::requestOptions()`, whose pin shares the 5-minute verdict cache, so a changed address can fail a ping for up to that long; `violation()` stays lenient about an unresolvable name, request time does not). A new outbound call to a subscriber- or staff-set URL must send with its guard's `requestOptions()`, never just `violation()`. Pinning does nothing behind an environment HTTP proxy.

## Webhook proxy/header guards, no Spatie retries with dispatchSync, and a wall-clock budget for synchronous retries
(1) A webhook channel's proxy_url is subscriber-controlled: it must pass WebhookUrlGuard::proxyViolation() at save AND send time. Its rules deliberately differ from the target URL's (http allowed, credentials allowed, ports 80/443 allowed alongside >=1024) — not an oversight. Extra headers must pass WebhookHeaderGuard at both points too (reserved names incl. Host, Content-Length, Content-Type, Transfer-Encoding, Connection, Upgrade, TE, Trailer, Proxy-Authorization, Proxy-Connection and the configured Signature/Timestamp names). Proxy URL and header values are secrets: like the signing secret and endpoint they must never reach a DeliveryResult error, a log or the activity log. The DNS-vs-client TOCTOU also applies to the proxy host. (2) Never hand Spatie maximumTries() > 1 together with dispatchSync(): the job release()s itself after a failed non-final attempt and returns without throwing, so throwExceptionOnFailure() never fires and the caller records a successful delivery that never happened. Retrying belongs in WebhookTransport's own loop, taking waits through App\Support\Delivery\Pauser so tests bind a recording no-op instead of sleeping. (3) A synchronous transport with subscriber-configurable retries/timeouts needs a wall-clock budget (WebhookTransport::DELIVERY_BUDGET_SECONDS = 50), not just per-attempt bounds: stay under min(queue retry_after, worker --timeout) (90 s / 60 s in config/queue.php) because exceeding retry_after causes a DUPLICATE delivery. Project the next attempt's cost before starting it, and keep in-request sends (confirmation codes) to a single attempt.

## Email channels send through Laravel Mail
The Email channel type uses ChannelTransport::Mail: MailTransport sends App\Mail\ChannelMessageMail (a Markdown mailable, body in an escaped <pre>) through the configured default mailer to the encrypted config['to'], never through Apprise. Failure text is fixed (missing address / mail server could not send): an exception message can carry the SMTP host, credentials or the recipient address. The shared mail theme header (resources/views/vendor/mail/html/header.blade.php) renders the logo from APP_URL plus APP_NAME for every Markdown email, including Filament's; keep custom emails on the Markdown layout so they inherit it. The SMTP mailer timeout is 10 s (MAIL_TIMEOUT) so the synchronous send stays well under the queue worker timeout, per the wall-clock-budget rule above. When `$meta['daily_summary']` is present (a Full Daily Summary for a channel type whose `supportsRichContent()` is true), MailTransport sends App\Mail\DailySummaryMail instead, with the same relay/address checks and fixed failure text; it is still the Markdown layout, with the radar image embedded inline as `cid:radar-snapshot`. DailySummaryMail must be sent, never queued: its constructor registers a closure, so only the plain-data report array travels on the queue. Every other channel type stays on Apprise.

## Channel types caption their destination value
Every channel type implements `destinationLabel()`, a short FIXED caption ("Pushover user key", "Email address") shown in gray under `displaySummary()`'s value in the subscriber's Channels table, so a masked fragment is never an unexplained string. The caption is never derived from the record, so it cannot carry a secret, and `displaySummary()` must still never return a value that alone grants delivery access. A new channel type must supply both; the table shows no caption when the value is `—`. Telegram's value is the bare chat ID (the caption says what it is).

## Mobile push goes through FcmClient: fixed strings only, a delayed token-guarded prune
`MobilePushTransport` sends through `App\Support\Delivery\FcmClient` (service-account JWT signed with openssl; token cached ~55 min; fixed hosts `oauth2.googleapis.com` and `fcm.googleapis.com`; redirects off; one attempt). The device's FCM token is a secret: `FcmResult` and `DeliveryResult` errors are fixed strings plus the numeric HTTP status, never a response body, exception message, token or credential (the body is read only to recognise an `UNREGISTERED` / invalid-token reply). When FCM says the token is dead, the transport queues `PruneMobilePushChannel` with a 60 s delay (so `DeliverWeatherAlert` writes its log row first) and a hash of the failed token; the job deletes the channel only if it still holds that token, so a phone that re-registered survives. On the device the app receives `TokenGenerated` only through the mounted screen's `#[On]` handler (trait `HandlesPushToken` on the Alerts feed, Rules, Locations, Account and welcome-flow screens); the plain `RegisterPushToken` listener is only a background fallback. `PushRegistration::register()` must not gate on the OS permission: Android reports `denied` until the dialog answer, which is recorded after the token event. Every message expires after one hour (`android.ttl` 3600s and the `apns-expiration` header), so a phone that was off never receives stale warnings: FCM's default is four weeks. The plugin creates and owns the high-importance Android notification channel `fcm_default_channel`: every message names it (`android.notification.channel_id`), because without it Android shows a background push in the SDK's fallback "Miscellaneous" channel (default importance, no heads-up banner; seen on the emulator). Device channels (`mobile_push`) are created only by the registration API, are verified on creation, do not use Free's no-cost channel slot and are hidden from the picker through `isAvailable() === false`. The iOS app icon badge is the subscriber's number of unread app alerts including the one being pushed: for an iOS phone (`config['platform'] === 'ios'`) the transport computes it AFTER the blank-token check with `App\Actions\Alerts\PushBadgeCount` and sends it as `aps.badge` (never a `data` field); Android gets none. `PushBadgeCount` is `CountUnreadAppAlerts` (unread groups, shared across phones) plus one unless the pushed alert's group is already unread (with a product, an unread successful push row with the same rule, NULL-safe, and product; without a product but with a batch key, an unread successful push row of the same batch, e.g. the other phone's push of the same run, so the second phone's badge is the plain unread count; with neither, an old queued job, always a new group). It adds rather than reads the alert because the jobs write the delivery row AFTER the send. The group arrives as `$meta['alert_rule_id']`/`$meta['ingested_product_id']`/`$meta['batch_key']` from `DeliverWeatherAlert` and `DeliverScheduledAlert` (a new pushing job must add them, or its push counts as a new group); `WebhookTransport` drops all three (`INTERNAL_KEYS`); Mail, Apprise, Web Push and the FCM data read only named keys, so none of them is sent anywhere. Only `$meta['type'] === 'alert'` (the default) counts as an alert, so the test push carries the plain count. Two near-simultaneous pushes can be off by one; no lock is taken because the app corrects the icon from the feed's `unread_count`. A failing count (a query error, or new code running before the `read_at` migration) must never fail the push: `badge()` catches it, logs only the exception class and sends without `aps.badge` (the jobs have no retries, so a thrown count would lose the alert).

## Device channels are deleted outside the dashboard, so they bypass ChannelDeletionGuard
`mobile_push` channels disappear without the dashboard delete path: sign-out, a dashboard revoke, Account "Turn off", an `UNREGISTERED` prune, and a new sign-in claiming the same token all delete the channel, and the cascade removes its `alert_rule_notification_channel` rows. `ChannelDeletionGuard` only covers dashboard deletes, so a rule whose only channel was the phone goes quiet silently. The safety net is the "alert with no channel" (`alert_no_channel`) row in `GetAlertsNeedingAttention` (the My Alerts "Needs attention" widget). Two test traps: the `sync` queue driver (phpunit) ignores `PruneMobilePushChannel`'s 60 s delay, so an end-to-end `DeliverWeatherAlert` test with an `UNREGISTERED` token would prune the channel before the `DeliveryLog` row exists (production uses the database queue); and the prune job's payload hash is a sha1 of the token compared with the channel's CURRENT token, not the SHA-256 `device_token_hash` column.

## A push about a stored bulletin carries an app link, never an https address
`MobilePushTransport` sends the data `url` the nativephp firebase plugin follows on tap. For an alert whose meta `url` is a public View Product page (`https://host/view-product/{slug}`, nothing else: no query, port or credentials) it is `config('wxnotify.app_product_uri')` + `/` + the base64url of that page address (`wxnotify://product/{link}`, matched by the app's `/product/{link}` route and checked again there by `ProductLinkTarget`); every other push (daily summary, threshold, lightning, the test push, a non-https `APP_URL`) sends `/`, which opens the feed. Do not send the https page address as the `url`: on Android the plugin would put it in the intent data and the phone's browser opens instead of the app. The app link's scheme and host must stay equal to the app's registered scheme and route.

## Only the unread count sets the icon badge; opening the app does not clear it
The iOS icon number is set in exactly two places: the push's `aps.badge` (above) and, in the app, `App\Services\AppBadge` (the local badge-count plugin; never throws), called by `AlertReadState` from the feed's `meta.unread_count` and after every read change, and by `SignOut::clearLocal()` (`AppBadge::clear()`). Sign-out ALSO calls the firebase plugin's `PushNotifications::clearBadge()` (`cancelAll()` on Android, so the previous account's alerts never stay in the tray; a harmless second zero on iOS); each call has its own try/catch, so one failing never skips the other and the sign-out always completes. This one-off foreground call is fine: the old ban on `clearBadge()` was about a background tick wiping a push that just arrived. Opening a tab screen (Alerts, Map, Products, Settings) must not touch the badge or call the server for it, and no screen polls for it: `TabScreensBadgeTest` holds this. The older design is retired: the per-phone counter, the app's reset call, the foreground-push flag and the 5-second check on the tab screens are gone from the code. What stays for old app builds, to be removed together in a later release: `POST /api/v1/push-token/badge/clear` (a 204 no-op, see api.md), the unused column `notification_channels.unread_push_count` (also a rollback safety; nothing may read or write it) and the FCM data keys `event` = `App\Events\ForegroundPushReceived` / `payload` = `{}` (`MobilePushTransport::FOREGROUND_PUSH_EVENT`/`FOREGROUND_PUSH_PAYLOAD`; a current build has no such class and the plugin only logs that it does not exist; they still cost an ephemeral PHP boot per foreground push and suppress the plugin's Android lifecycle post, so removing them is worthwhile).

## A no-product alert sent to several channels shares one batch key
`DeliverScheduledAlert` (daily summary, threshold, lightning) is queued once per channel. The dispatcher (`DispatchScheduledAlerts` per rule per run, `MatchLightningFlashes` per rule per alert) creates ONE `(string) Str::uuid()` and passes it as the job's optional last argument `$batchKey` to every job of that run; the job writes it to `delivery_logs.batch_key` on every row it creates (success, failure, skipped) and puts it in the meta. The app's feed groups no-product rows by it, so a summary pushed to two phones is one alert, one unread and one read (see api.md). A new dispatcher of a no-product alert must do the same, or each channel's row is its own alert. `$batchKey` is read once as `$this->batchKey ?? null` (a job queued before it existed has it uninitialized and writes NULL, the old one-row-per-alert behaviour). Deploy is backend only: run `migrate` (non-transactional, re-runnable: adds the nullable column when missing and rebuilds the partial index `delivery_logs_batch_key_index` (`user_id, batch_key` where `batch_key IS NOT NULL`) CONCURRENTLY; check `indisvalid`), no backfill, no app change (feed shape, ids and endpoints are unchanged; a batch's id is its lowest row id).

## Read/unread alerts deploy order
Backend first: stop the queue worker (prefer this over running `migrate` straight after the pull, since `queue:listen` picks up new code on the next job), run `migrate` (if it fails, keep the worker stopped and re-run it before restarting: a re-run with the new code live would mark pushes that arrived meanwhile as read), then check `SELECT indisvalid FROM pg_index WHERE indexrelid = 'delivery_logs_unread_push_index'::regclass;` is true (the migration is non-transactional and safe to re-run: it adds `read_at` only when missing, backfills only rows still unread, and drops and rebuilds the index, so an interrupted CONCURRENTLY build never stays INVALID), restart the worker, and only then ship the native app rebuild. A new app against the old backend leaves the iOS icon climbing: the old backend keeps counting per phone and the new app no longer resets it.

## The app's read state is local first, retried, and sets the icon badge from the unread count
In the mobile app `App\Services\AlertReadState` owns read/unread: `open($id)` (a list tap and `AlertDetail::mount()` both call it; an alert the phone already shows read with nothing pending sends no request) and `markAll()` mark the cache at once (`cached_alerts.read`, default true so rows cached by an older build count as read; the stored count `wxnotify.alerts.unread_count`), then call `POST /api/v1/alerts/{id}/read` / `POST /api/v1/alerts/read-all` best-effort and store the server's `unread_count`. A failed call is queued (`wxnotify.alerts.pending_reads`, ids; `wxnotify.alerts.pending_read_all`, a flag) and `retryPending()` replays it at the start of every first-page feed load (`AlertsScreen::refreshFeed()`): a 404 drops an id, offline, a 429 or a refused token stops the replay and keeps the queue (the feed load that follows signs out on 401; never retry in a loop), any other failure keeps that id. An id already pending never lowers the count again, and neither `applyFeed()` nor `LocalCache::storeDetail()` turns a pending read (or anything under a pending mark-all) back to unread, otherwise a refused read POST followed by the detail's `read:false` counts one read twice. `applyFeed()` keeps queued reads read in a fresh page (a pending mark-all shows everything read and a zero count) and syncs the stored count and the icon badge (`AppBadge::set()`) from the page's `meta.unread_count` less those reads; every read change sets the badge too. The service never throws to a screen and never blocks opening an alert. `LocalCache::wipe()` (sign-out) forgets the count and both pending keys. Tests bind `Tests\Fakes\RecordingAppBadge` by default (`tests/Pest.php`, it records the numbers); `AppBadgeTest` forgets it to test the real plugin call. Test trap: `Http::fake()` evaluates every URL stub for each request, so a `Http::sequence()` under `wx.test/api/v1/alerts*` is also consumed by the `/alerts/{id}/read` calls: fake the feed as `wx.test/api/v1/alerts?*`.

"Mark all as read" only reads what the phone had loaded. `AlertsScreen::refreshFeed()` stores the first page's `meta.as_of` (`wxnotify.alerts.feed_as_of`; `loadMore()` pages never replace it; a page without one, an older backend, forgets it). `AlertReadState::markAll()` reads it at tap time and sends it as `through` (see api.md); locally only alerts whose `dispatched_at` is strictly before the cutoff's whole second turn read (`App\Support\ReadCutoff::covers()`, real date parsing, the same rule as the server's `created_at < startOfSecond(through)`; an unparsable time stays unread) and the count becomes the cached feed's alerts still unread. A failed call stores the CUTOFF STRING in `wxnotify.alerts.pending_read_all` instead of `true`, so `retryPending()` replays the original cutoff, never a fresh one; a stored `true` (an earlier build) or no `as_of` at all means no cutoff: read everything and count zero, as before. `applyFeed()` and `storeDetail()` apply the same rule for a pending mark-all with a cutoff, so an alert newer than it stays unread. A successful mark-all with a cutoff keeps the pending single reads instead of dropping them and replays them at once (idempotent), so the stored count, the server's, never includes an alert already shown read. `dispatched_at` and `created_at` are both `now()` in the same `DeliveryLog::create` after the send, so app and server agree, except where a group's `dispatched_at` (`latestAt`) comes from a non-push row: that only makes the app keep a dot the server may have cleared, the safe way, and the next feed load corrects it. `LocalCache::wipe()` forgets the as_of key too.

## The mobile welcome flow shows once per install and asks for nothing on Skip
After the first sign-in `AuthCallback` replaces itself with `/welcome` while `Welcome::shouldShow()` (the flag `wxnotify.welcome.seen`, `WelcomeState`) is unset; the flow sets it at mount. The flag lives in its own cache key, which sign-out never touches and uninstalling removes; never put it in secure storage (that survives an uninstall on iOS). An install that was already signed in before the flow existed is marked seen by `AlertsScreen::mount()` (`markLegacyInstallSeen()`, only with a token). The steps are welcome, offer, push, location, done: the push step is left out when push is already on or the OS refused it, the location step when sharing is not off (on, or 'waiting' for the OS permission) or the slot lookup did not answer true. The lookup is `can_share_phone_location` from `GET /api/v1/alert-rule-options`, made once in `Welcome::steps()` with a 4 s timeout (`alertRuleOptions(4)`; every other caller keeps 15 s) so a slow server never holds up the first screen; `Welcome::phoneSlot()` keeps its answer (true / false / null for failed, timed out, offline or key missing). With sharing off and no Location step, the last screen says "Your plan's phone-location allowance is used up..." only when the server answered false (or `LocationSharing::enable()` returned `limit`), and otherwise the neutral "You can share this phone's location later from Settings → Account." (no plan claim). Deploy order: an app that reaches phones before the backend sends `can_share_phone_location` shows no Location screen and the neutral note. Skip leaves from any step and asks for nothing: no OS dialog, no "declined" mark. Location is deliberately NOT pre-checked against the OS permission (the plugin's check is async); the system dialog comes only from the Share location button. A denied OS location permission does NOT surface as an `enable()` failure: the plugin's start is async, so `enable()` returns `started`, the phone slot is used, the flow shows no note, and Account later shows sharing 'waiting' for permission (recoverable there with Stop sharing). Settings -> Welcome tour replays it at `/welcome/tour` and must open it with `navigate` (never `replace`): it closes with `back()` and never touches the flag.
