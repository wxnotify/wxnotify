# Actions

## Activity causer: causedBy() is ignored; pin with CauserResolver::withCauser
AppServiceProvider's CauserResolver `resolveUsing` closure ignores the `causedBy()` subject: it returns `auth()->user()`, or the impersonator. A session-less request (the app token exchange, queued jobs) therefore logs a null causer unless the call is wrapped: `app(CauserResolver::class)->withCauser($user, fn () => activity()->...->log(...))`.

## Alert rule persistence lives in SaveAlertRule
`CreateAlertRule` and `EditAlertRule` (dashboard) and `AlertRuleController` (API) all persist through `App\Actions\Alerts\SaveAlertRule` (`attributes()` for the columns, `syncRelations()` for the pivots). A change to what a rule save does belongs in that action, not in a Filament page hook or a controller, and needs a case in `AlertRuleParityTest`.

## SaveAlertRule is the one writer of per-product matching settings
A product-based rule (Weather Alerts, SPC & WPC) stores how each product matches on the `alert_rule_product` pivot (`matching_mode`, `wfo`, `county_zone_codes`) and in `alert_rule_product_location`; `SaveAlertRule` writes both, nothing else does. Input is `product_settings` (a list of `{product_id, matching_mode, location_ids, wfo, county_zone_codes}`) or the flat `product_ids` with `matching_mode`, `location_ids`, `wfo`, `county_zone_codes`, which `productSettings()` expands to the same list (one shared setting for every product), so an old client behaves as before. A mode's unused settings are cleared (a non-WFO product keeps no WFO, only County/Zone keeps codes, only the location-based modes keep locations), and the pivot rows and the per-product location rows are replaced together in one transaction, with no orphans. Location ids are scoped to the rule owner here as well as in validation. The rule's own `matching_mode`, `wfo`, `county_zone_codes` and the `alert_rule_location` pivot are no longer written for a product-based rule (they are nulled/emptied; the columns stay in the schema for one release as a rollback net and a later change drops them), so nothing may read them except `AlertRule::settingsFor()`'s inherit path for a pivot row with no mode (`.ai/rules/pipeline.md`). Keep path: two layers decide it. For the API, the REQUEST layer (`SaveAlertRuleRequest::PRODUCT_KEYS`: `product_ids`, `product_settings`, `matching_mode`, `location_ids`, `wfo`, `county_zone_codes`, `risk_levels`, and the same category as stored) decides whether a PUT keeps the stored products: a PUT carrying none of those keys is not validated as product input. The ACTION itself keeps whenever both `product_settings` and `product_ids` are absent, ignoring any `matching_mode` or `risk_levels` passed on that path (through the API those keys never reach the action on that path, because the request layer validates and passes on nothing there; a direct caller can still send them). A kept save leaves the products, their settings and `risk_levels` untouched; the mobile editor relies on it to save a mixed rule's name, channels or quiet hours. The dashboard builds its input once from validated, dehydrated form data (`.ai/rules/filament.md`).

## A channel is created and sent its first code only through BeginChannelConnection
`App\Actions\Channels\BeginChannelConnection` stores the channel unverified, sends the confirmation code and removes a channel it just created when the code cannot be sent. The dashboard's `ConnectChannel` wizard and `POST /api/v1/channels` both call it; a change to what connecting a channel does belongs there, not in the page or the controller. It does not pin the activity causer (the wizard has a session, and impersonation attributes to the impersonator): the API controller wraps the call in `CauserResolver::withCauser`.

## GetMapWarnings selects through active_wwa_areas, never the event row's own columns
`App\Actions\Map\GetMapWarnings` reads an event's extent from its `active_wwa_areas` rows: an area's own polygon, else the boundary of the zone it names (public zones and fire zones by `state_zone`, counties by state and the last three digits of the FIPS, marine zones by `zone_id`). Do not fall back to `active_wwas.ugc_codes` or `polygon` (they only describe the latest bulletin of an event issued as many; see `.ai/rules/pipeline.md`). The expiry comparison binds Carbon's `now()` (not the database clock), so a test with a frozen clock keeps its fixtures consistent. The query caps anchors at 50 (after de-duplicating, keeping the given order) and its SQL was tuned against the dev data (family pre-filter, geometry resolved once in MATERIALIZED CTEs, a per-anchor bounding box before the exact distance), so a change to it should be timed on realistic data. Identical geometries of one event are de-duplicated (a storm-based warning repeats one polygon on every zone row it covers).

## SearchProducts owns the product archive search and mirrors the product page's test-product rule
`App\Actions\Products\SearchProducts` is the only query behind `GET /api/v1/products`. It selects only the listed columns (never `text`), pages by `(received_at, id)` through `AppAlertCursor`, and hides `is_test` products in production like `ViewProductController`. What it matches: the catalog name, the AWIPS ID prefix and the WMO header prefix, plus (for catalog products with a 3-character AWIPS category code) the unclassified rows of that category, in both the text match and the `type` filter. A change to what the archive search matches belongs here.

## GetActiveAlertsForUser reads events only through GetActiveAlertsForLocation::activeFor()
`App\Actions\Alerts\GetActiveAlertsForUser` merges the per-place results of `activeFor()` (the zone rows, `active_wwa_areas`) into one entry per event: the latest end across the affected places (none when any has none), the sorted place labels, and the latest bulletin's page. Never read an event's own `ugc_codes` or `polygon` here (`.ai/rules/pipeline.md`).
